# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Status

The project is being resumed after years idle (the README still says it's paused). Yoga (3.2.2), SDL3, GLFW and Skia (m159) are current.

## Building

The toolchain and system libraries come from the Nix flake's dev shell (`flake.nix`), loaded by direnv (`.envrc`: `use flake`); outside direnv, prefix commands with `nix develop -c`. The flake is a convenience for local development only: the build must also work without Nix, so never make a dependency reachable only through it. Yoga, Skia and `lib/psychic-color` are git submodules; CMake stops with a fatal error if they are missing. SDL3 and GLFW come from `find_package` (`SDL3 3.2`, `glfw3 3.4`, both in the flake), otherwise FetchContent downloads a pinned release (SDL 3.4.20, GLFW 3.5.1, by URL and SHA-256) and builds it static: SDL3 without audio, joystick, haptics, sensors, camera, GPU, render, Vulkan or the X11 extensions it would otherwise stop on when their headers are missing (XScrnSaver, XShape, XTest, Xdbe), GLFW with Wayland only when its development files are found and SDL3 isn't fetched too (both static, their generated Wayland protocol symbols would clash). `-DCMAKE_DISABLE_FIND_PACKAGE_SDL3=ON -DCMAKE_DISABLE_FIND_PACKAGE_glfw3=ON` forces the downloads. `CMakePresets.json` has `debug` and `release` presets that build in `build/<preset>` and export `compile_commands.json`:

```sh
git submodule update --init --recursive
cmake --preset debug
cmake --build --preset debug -j"$(nproc)"
```

No preset sets a generator, so it stays CMake's default (Make), not Ninja; pass `-j` yourself.

- CMake 3.24 or newer.
- Everything is a target: psychic-color is the static `psychic-color::psychic-color`, Yoga is its own static `yogacore` target, linked PRIVATE (no public header includes Yoga: `Div.hpp` only forward-declares `YGNode`; measurable divs override `Size measure(Constraint width, Constraint height)` from `Measure.hpp`, with `Fit::Exact`, `AtMost` or `Unbounded`, converted from Yoga in `Div.cpp`; the tests link `yogacore` themselves to inspect nodes) (`extlib/external/yoga/yoga/CMakeLists.txt`, added from `extlib/yoga/`; it compiles as C++20 with `-Wall -Werror` in its own directory), Skia the imported `Skia::Skia`, SDL3 `SDL3::SDL3`, GLFW `glfw`. ICU and Fontconfig use CMake's own Find modules; there's no `cmake/` directory any more. On macOS the Homebrew prefix comes from `brew --prefix`.
- Skia (`chrome/m159`) is built by `extlib/skia/skia_build.sh.in`, which CMake runs as the `skia-build` custom command when one of its static libraries (`libskia.a`, `libskparagraph.a`, `libskshaper.a`, `libskunicode_icu.a`, `libskunicode_core.a`, `libskcms.a` in `<build dir>/extlib/skia/build`) is missing: it runs Skia's `bin/fetch-gn` (needs network; the downloaded `gn` binary runs through nix-ld), and `bin/fetch-ninja` only when CMake found no `ninja`, then `gn gen` and `ninja` for those targets, all with Python 3. No `git-sync-deps`: every third-party library Skia uses comes from the system (ICU, HarfBuzz, FreeType and Fontconfig on Linux; ICU, HarfBuzz and CoreText on macOS), and image codecs, PDF, SVG, Skottie, Graphite, Vulkan, Metal and Skia's own GL loaders are off. The gn args are in `extlib/skia/CMakeLists.txt`, with the compilers CMake uses (`cc`/`cxx`). The first Skia build is slow; copying an existing `extlib/skia/build` into a new build directory (`cp -a`) before its first build skips it.
- `Skia::Skia` is an interface target over those libraries: Skia's source root as include directory (`#include "include/core/SkCanvas.h"`, `"modules/skparagraph/include/Paragraph.h"`), the public defines of the configuration it was built with (`SK_RELEASE`, `SK_GANESH`, `SK_GL`, the shaper, unicode and paragraph ones; keep them in step with the gn args, `gn desc <out> //:skia defines` lists them), HarfBuzz, ICU, and FreeType and Fontconfig or the Apple frameworks.
- CI (`.github/workflows/ci.yml`, GitHub Actions) proves the build works without Nix, from system packages: Linux on `ubuntu-24.04` (it has no SDL3 or GLFW 3.4, so they're fetched, with their X11/Wayland development packages installed; its default GCC 13 lacks C++23 deducing this, so the job installs `g++-14` and passes it to CMake, which passes it on to Skia's gn), and macOS; both jobs are required. Both cache Skia's output directory per Skia commit and build script.
- The library requires C++23 (`target_compile_features(psychic-ui PUBLIC cxx_std_23)`), so whatever links it builds as C++23 too: the chainable API uses explicit object parameters ("deducing this"), which need GCC 14+, Clang 18+, Apple Clang 16+ or MSVC 17.2+. The root `CMakeLists.txt` stops at configure time with an older compiler, which would otherwise accept `-std=c++23` and fail deep in the headers.
- CMake options (all `ON` by default): `BUILD_SHARED_LIBS` (builds psychic-ui as a shared library; Yoga, psychic-color and a fetched SDL3, GLFW or Catch2 stay static either way), `PSYCHIC_UI_BUILD_SDL3` (the runner and the SDL adapter; the demo and playground need it), `PSYCHIC_UI_BUILD_GLFW_ADAPTER`, `PSYCHIC_UI_BUILD_TESTS`, `PSYCHIC_UI_BUILD_EXAMPLE`, `PSYCHIC_UI_BUILD_PLAYGROUND`.
- Non-Debug shared builds strip the library after linking; use the `debug` preset when debugging.
- `make doc` generates Doxygen docs when Doxygen is installed. `docs/html/` holds committed generated output, so don't edit it by hand.
- **Library sources are listed explicitly in `SOURCE_FILES` in the root `CMakeLists.txt`.** A new `.cpp`/`.hpp` must be added there; test files go in `tests/CMakeLists.txt`.

## Tests

Catch2 v3 into one executable, linked to `Catch2::Catch2WithMain` (there's no `main.cpp`) and registered with CTest. `tests/CMakeLists.txt` uses an installed Catch2 3 when `find_package` finds one (the flake provides `catch2_3`) and it passes a check; otherwise FetchContent downloads `v3.16.1` into `<build dir>/_deps`. The check builds `tests/catch2-check/` with `try_compile` (a project of its own, so the installed Catch2's targets can't clash with the download): it must link a program that stringifies a `std::string_view`, because Catch2's library only defines that `StringMaker` when it was itself compiled as C++17 or newer, while our C++23 build of its headers expects it. Without an installed Catch2 the check project still configures and fails to build (`not_found.cpp` `#error`s a marker), since an error while configuring it would stop ours. The download is built as C++23 (`CMAKE_CXX_STANDARD` set around `FetchContent_MakeAvailable`): Catch2 only asks for C++14, which is what AppleClang (whose default is older) then compiles it as, so the downloaded library lacked that `StringMaker` on macOS and the tests failed to link (GCC 14 defaults to C++17, which hid it on Linux). The configure prints which Catch2 it uses and why; a failed check's output goes to `<build dir>/tests/catch2-check.log`. The result is cached and rerun when the compiler, flags, build type, prefix path, ignored paths or `Catch2_DIR` change. `-DCMAKE_DISABLE_FIND_PACKAGE_Catch2=ON` skips the check and forces the download. `lib/psychic-color`'s own tests (`PSYCHIC_COLOR_BUILD_TESTS`) default off when it isn't the top-level project, so they aren't built here.

The backend tests (`tests/backends/`) need no display: a fake `SystemWindow`, SDL3 on its `dummy` video driver fed synthetic events (finger events too, from a made-up touch screen), and GLFW on its null platform with its installed callbacks called directly. Touch gestures are tested with explicit times (`touch_tests.cpp`).

```sh
ctest --preset debug                                       # all tests, through CTest
./build/debug/tests/psychic-ui-tests                       # all tests
./build/debug/tests/psychic-ui-tests "[style]"             # by tag
./build/debug/tests/psychic-ui-tests "basic style getter"  # by test name
```

## Executables

- `example/` builds `psychic-ui-demo` (SDL3): the demo app, where new components are developed before they move into the library. It is an `AppShell` (`example/demo/DemoWindow.hpp`): the sidebar lists the pages (Controls: Buttons, Ranges, Text Input, Inputs, Lists, Popups; Layout: Typography, Divs, Scroller; Assets: Colors, Icons) and, at the bottom, a Theme item opening a menu of themes (System first); a page shows in the inset panel under a `PageHeader` holding the menus and a tool bar. Icons (`example/demo/Icons.hpp`) shows every registered icon at 14 and 20 px with its name, under Inter samples at 11 to 14 px; Lists (`example/demo/Lists.hpp`) shows every list component, a data grid with an inspector that follows its selection. Popups (`example/demo/Popups.hpp`) shows a menu with every kind of row, a context menu, selects, tooltips, dialogs and toasts. Arguments: `--theme <system|pivotal-dark|pivotal-light|one-dark|one-light|psychic>`, `--page <name>` (as in the sidebar), `--no-fps` (hides the frame counter, for screenshots), `--open <menu|submenu|context|select|dialog|confirm|toasts|tooltip>` (shows the Popups page with that popup open, for screenshots). It also builds `psychic-ui-glfw-host`, a GLFW application that embeds a Psychic UI window through the GLFW adapter (Escape quits).
- `playground/` builds `psychic-ui-playground` (SDL3), a scratch app.

Resources (`res/`, `example/fonts/`) are copied into the build directory, and fonts load by relative path, so run binaries from their build directory.

Bundled fonts live in `res/fonts/<family>/`, each with its license: Ubuntu (`UFL.txt`) and Inter 4.1 (`OFL.txt`, SIL OFL 1.1), Pivotal's typeface: the hinted static TTFs `Inter-Regular.ttf`, `Inter-Medium.ttf` and `Inter-SemiBold.ttf` from `extras/ttf/` of the official release `Inter-4.1.zip` (github.com/rsms/inter, SHA-256 `9883fdd4a49d4fb66bd8177ba6625ef9a64aa45899767dde3d36aa425756b11e`; its `InterVariable.ttf` and `Inter.ttc` match nixpkgs' `inter` 4.1 byte for byte). A theme's `Typography` names its `regular`, `medium` and `semiBold` fonts: Inter ("Inter", "Inter Medium", "Inter SemiBold") by default, Ubuntu (`themes::ubuntuType`: "Ubuntu Regular", "Ubuntu Medium", "Ubuntu Bold") in the One and Psychic themes. `DefaultSkins` loads both families and the theme's (the style manager loads a name once), so any style can use `fontFamily("Inter")`. The tests load fonts from the sources (`PSYCHIC_UI_TEST_FONTS`, `PSYCHIC_UI_TEST_RES`).

- `SDL_LOGGING=app=debug` makes the SDL3 runner print the video driver, GL renderer, samples, stencil bits, hit testing and pixel density it got.
- SDL picks the video driver (decision D4). Under WSLg it falls back to XWayland by itself (the compositor lacks fifo-v1); `SDL_VIDEO_DRIVER=wayland` forces Wayland, which works too. Nix's Mesa only finds WSL's GPU driver with `LD_LIBRARY_PATH=/usr/lib/wsl/lib` and `GALLIUM_DRIVER=d3d12`, which the dev shell sets when `/usr/lib/wsl/lib` exists; otherwise GL is llvmpipe (software).
- Under Xvfb, unset `WAYLAND_DISPLAY` and point `XDG_RUNTIME_DIR` at an empty directory: otherwise GLFW (and SDL when forced) connects to WSLg's `wayland-0` socket and opens windows on the real display.

## Architecture

Retained-mode UI: **Skia** draws, **Yoga** does flexbox layout, and a CSS-like **style system** drives both. Everything lives in `namespace psychic_ui`.

- **`Div`** (`psychic-ui/Div.hpp`) is the base node, like an HTML div. It owns a Yoga node, children (`std::shared_ptr<Div>`, hence `enable_shared_from_this`), tag and class names, mouse/focus handling and signals. Override `draw(SkCanvas*)` for custom drawing; `render()` recurses over children. `add<T>(args...)` constructs a child and returns `T &`: the parent owns it (keep a raw pointer or reference to it, valid while it is a child); `add(child)` / `add(index, child)` add an existing `shared_ptr` and return it as `T &`. `children()` returns the vector by reference, in document order. The computed style is the only input of its Yoga node (`updateLayout` pushes it); `x()`/`y()`/`getWidth()`/`getHeight()` read the last layout. A component's own defaults go in `_defaultStyle`, which stylesheets override.
- **The API is chainable**: every style property has a setter on `Div` itself, generated from the property table, writing the inline style (`div.padding(24).overflow(Overflow::Scroll)`; read values back from `computedStyle()`, or `style()` for the inline ones), plus helpers (`row()`, `column()`, `size(w, h)`, `style(const Style &)` to overlay a reusable `Style`). Every mutator returns the most derived type through C++23 explicit object parameters ("deducing this"), so base and derived setters chain in any order: `add<Button>("x").enabled(false).toggle(true).padding(24)`. Setters and getters share the bare name (`enabled()` / `enabled(false)`, `text()` / `text("...")`, `selected()`, `checked()`, `value()`, `range(min, max)`...). To add one to a component: `template<class Self> Self &name(this Self &self, Arg value) { static_cast<Component &>(self).updateName(value); return self; }` with the work in a protected non-template `updateName`; an explicit-object function can't be virtual, so a setter that subclasses must react to calls a protected virtual hook (NVI, like `enabled()` → `enabledChanged()`, `text()` → `TextBase::updateText`). A subclass member with a property's name hides the generated setter: bring it back with a using-declaration (`Component::skin()` does `using Div::skin;`). Bool, string and number arguments use the `detail::*Arg` wrappers so misuse doesn't compile.
- **`Window`** is the root `Div`. `Window::drawAll()` runs each frame in this order, the first two in `updateStylesAndLayout()` (no canvas needed, which is how the tests drive it): styles (the whole tree if the `StyleManager` is invalid, otherwise `updateDirtyStyles`, which follows the `_descendantStyleDirty` flags that `invalidateStyle` sets up the parent chain, visible or not; repeated up to `maxStylePasses` times while `styleUpdated` callbacks invalidate more), then layout if the Yoga root is dirty or the window size changed (`YGNodeCalculateLayout` at `windowWidth()`/`windowHeight()`, which the root, with no size of its own, fills; then `layoutUpdated()`), then `render()` on the Skia canvas, which only paints: per Div, its shadows (`shadow*`, a blurred copy of its border box outside it, grown or shrunk by `shadowSpread`, like CSS `box-shadow`; `shadow2*` is a second layer under the first, for two-layer elevations), `draw()`, its children (clipped by `overflow`), then its `outline*` (a line `outlineOffset` outside the border box, over the children), so any Div gets a shadow or a focus ring whatever its `draw`; neither is inherited, so a skin doesn't repeat its component's (a Div with `opacity` below 1 draws itself and its children into a `saveLayerAlpha` layer, so the subtree fades as one group like CSS opacity; at 0 it draws nothing). Borders on some sides only (`borderTop`...) are drawn on the div's own edges.
- **Focus**: a press focuses the deepest div under it (`Window::requestFocus`); `:focus` matches a focused div that is `focusEnabled`. Tab and Shift+Tab (`Window::focusNext`) move the focus through the divs that take it (focusEnabled, enabled, visible; the topmost popup's that traps the focus, a menu or a dialog, else the app's), in document order, wrapping around; focus moved by the keyboard sets `Window::focusVisible()`, which `:focus-visible` also requires (like CSS's: a ring for the keyboard, none for a click). Buttons, check boxes, ranges and sidebar items take the focus: Space or Enter clicks a button, Space toggles a check box, the arrows, Home and End move a range. The deepest focusable div on the new path may hand the focus on to a descendant (`Div::focusDelegate()`, unless the path already goes through it): text fields (`TextInput`, `TextArea`, `SearchField`, `NumberStepper`) hand it to their text display, so Tab or a press beside the text lets one type. Skia is set up lazily on the first frame, with a GL interface assembled from the system window's `glProcAddress` (Skia's own GL loaders aren't built); the surface is the framebuffer's pixel size, remade on the frame after a resize, and the canvas is scaled by the pixel ratio. Every Yoga node is created with one shared config (web defaults, rounding disabled), owned by `Div.cpp`. The system window's visibility is `windowVisible()` (`close()` turns it off), separate from the `visible` style, which hides a Div from painting and hit testing but keeps it in the layout.
- **Backends** (`psychic-ui/applications/`): `SystemWindow` (`SystemWindow.hpp`) is the platform side of a `Window`: sizes (window units for input and layout, framebuffer pixels for drawing), GL proc addresses, window operations, drag support, text input, clipboard, the system's light or dark mode (`colorScheme()`, `Unknown` by default, which GLFW keeps). Adapters implement it over a window they don't own and translate its events: `SDL3SystemWindow` (`handleEvent(const SDL_Event &)`, `installHitTest()`) and `GLFWSystemWindow` (installs its callbacks over the host's and chains to them, like Dear ImGui's `imgui_impl_glfw`). `SDL3Application` is the only runner: SDL init, one SDL window and GL context per `Window`, the loop. There is no application interface; embedding hosts have no application object. A system window detaches from its `Window` in its destructor, with its context still current.
- **Touch and pens**: `Window::inputMode()` is `InputMode::Pointer`, `Touch` or `Pen`, set by the backends through `handleInputModeChange` (`onInputModeChange`/`inputModeChanged`); in touch mode `:touch` matches every div of the window (`Window:touch Button`). The SDL3 adapter follows the first finger on a touch screen (`SDL_TOUCH_DEVICE_DIRECT`; trackpads, other fingers and the mouse events SDL makes of touches and pens are ignored, so a tap arrives once; `touchDeviceType` is virtual for the tests) and calls `Window::handleTouchPress`/`Move`/`Release`/`Cancel` with SDL's timestamps; real mouse motion or buttons switch back to pointer. The window turns touches into mouse events: a tap clicks where the finger landed; past `touchSlop` (8 px) it pans the deepest `overflow: scroll` div under the finger that can scroll along the drag's main axis, else it presses there and drags; held `longPressDelay` (500 ms) it is a right button press, released when the finger lifts, which never clicks (and asks for a context menu). Its mouse events say `source` `Touch`. A pan that lifts while moving flings (kinetic scrolling, decaying by `flingDecay` per ms), advanced by `updateGestures(time)`, which `drawAll` calls each frame with the system window's `gestureTime()` and tests call with their own times; a finger stops it. A pen is a mouse in pen mode (tip left, barrel buttons right and middle). GLFW has no touch input: its adapter never changes the mode. In touch mode a focused text field tells the system window its caret's line (`setTextInputArea`, `SDL_SetTextInputArea` in SDL3) so the on-screen keyboard avoids it.
- **Light and dark**: a window follows the system's color scheme until a theme is picked (`followsSystemTheme()`): the skin set's `lightTheme()` while the system is light, its `defaultTheme()` while it is dark or doesn't say (`SkinSet::theme(scheme)`), switched live; `Window::theme(t)` stops following, `followSystemTheme()` resumes it, optionally with a pair of themes. The system window reports the scheme when it attaches and on changes (`Window::handleColorSchemeChange`, then `colorSchemeChanged`/`onColorSchemeChange`): the SDL3 adapter from `SDL_GetSystemTheme` (`colorScheme()` is virtual for the tests) and `SDL_EVENT_SYSTEM_THEME_CHANGED`, which names no window, so `handleEvent` takes it whatever window and `SDL3Application` sends it to every window.
- **Overlay and popups** (`Overlay.hpp`): the window's last child, above `appContainer()`, is its `Overlay` (`Window::overlay()`), filling it; its children are `Popup`s, the last on top: menus, select lists, tooltips, dialogs, the toasts' stack. `overlay.open<T>(args...)` (or `open(shared_ptr)`) adds one on top and calls its `opened()` (where it takes the focus), `popup.close()` removes it (the popups it owns first, `owner(popup)`: a submenu) and emits `closed`. A popup is placed beside an anchor, a div (`anchor(div)`, held weakly: it closes when the div leaves the window) or a point in window coordinates (`anchor(x, y)`), on a `side` (`Side::Bottom`, `Top`, `Right`, `Left`) with an `alignment` (`PopupAlign::Start`, `Center`, `End`), `sideOffset` and `alignOffset`, by `placePopup` (a pure function: it flips to the opposite side when it doesn't fit and that side fits or has more room, then shifts along the side to stay inside the window less `collisionPadding`, 12); `updateStylesAndLayout` places the anchored popups after the layout (`Overlay::place`) and lays out again when one moved, every frame, so a popup follows its anchor; `placedSide()` and `anchorRect()` say where it went (a tooltip's arrow). Unanchored, a popup sits where its style puts it (a dialog fills the overlay, the toasts' stack is in a corner). Mouse input: the overlay only takes it where a popup does (`Overlay::dispatch`, topmost first; a popup with neither `mouseEnabled` nor `mouseChildren` lets it through, a tooltip), and everywhere under a `modal` popup, which keeps it from the content and the popups under it except its `passThrough(div)` divs (a menu bar, so that hovering another trigger switches menus); the window's hit path (`hitPath`, used by hit slop, touch panning and tooltips) follows the same rule, and `isDragArea` is false under a modal popup or on a popup. Dismissal: before a press is dispatched, `Window::handleMouseButtonChange` calls `Overlay::pressOutside`, which closes, topmost first, the popups the press is outside of (outside their `surface()`, a dialog's panel) that `dismissOnOutsidePress` (the default), stopping at one it is inside of, a pass-through div, or a modal popup that stays; when that closed a modal popup, the press and its release go no further. Escape closes the topmost popup that `dismissOnEscape` before the focus path sees the key (`Overlay::dismissTop`). Focus: `trapFocus` keeps Tab within the topmost popup that traps it (`Overlay::focusScope`); a popup notes what had the focus when it opened and, closing with the focus inside it, gives it back with the same `focusVisible` (`restoreFocus`, the default). `Window::updatePopups(now)` advances what goes with time (tooltip delays, toast timers), from `drawAll` with the system window's `gestureTime()` like `updateGestures`, and from tests with explicit times.
- **Menus** (`components/Menu.hpp`): items are data (`MenuItem`: label, shortcut, icon, `enabled`, `danger`), made into rows each time a menu opens, so they keep their state: `Menu::item(label, callback, shortcut, icon)`, `Menu::item(label, items)` (a submenu), `Menu::check(label, checked, callback)` (toggled when chosen, the menu stays open), `Menu::radio(group, label, value)` (a `MenuRadioGroup` holds the value and its callback; `closes` makes choosing one close the menu, as a select's list does), `Menu::separator()`, `Menu::group(label)` (a group label). A `Menu` is a modal popup of `MenuButton` rows (`rows()`), `.separator` divs and `.group-label` labels; when one row has an icon every row keeps the icon column, and when one is checkable every row keeps the check column (`MenuButton::setColumns`; the `.check` part before the icon, or the `.indicator` part after the label with `checksAfter(true)`); a checked row has the `checked` class, a danger one `danger`. One row is highlighted (`highlight(index)`, its `selected` state, `:active` in rules) by hovering it or by the keyboard (the menu has the focus): Up and Down (wrapping, over disabled rows), Home, End, Right or Enter on a submenu row opens the submenu and moves into it, Left in a submenu closes it, Enter or Space chooses (`choose(index)`), Escape closes the topmost menu; Left or Right past a menu bar's menu opens its neighbor (`navigatedOut`). Submenus open beside their row (`Side::Right`, first rows level), flip left at the window's edge, and are not modal so that the mouse still reaches their menu; hovering opens them without moving the focus. `Window::openMenu(items, x, y)` (at a point), `openMenu(items, anchor, side, align)` (beside a div, 6 px away) and `openMenu(shared_ptr<Menu>)` close the open menu first, emit `menuOpened`, and `menuClosed` when it closes; `closeMenu()` closes it. `Window::openContextMenu(items, x, y)` opens one at a point with the `context` class: it is the hook for the context-menu request (right press, touch long press, Menu key), which nothing calls yet. `MenuBar` opens its menus under their triggers, as pass-through.
- **Select** (`components/Select.hpp`): a focusable closed field (`.value`, with the `placeholder` class while nothing is chosen, then `.chevron`) whose options (`options`, `selectedIndex`, `value()`, `placeholder`) open in a `Menu` with the `listbox` class below it, at least its width, the chosen option highlighted and checked after its label; a click, or Enter, Space, Up or Down, opens it; choosing emits `changed` (`onChange`) with the index; the field has the `open` class meanwhile. A press on the field while it is open closes the list (outside press) without reopening it.
- **Tooltips** (`components/Tooltip.hpp`): `div.tooltip("text")` (a `Div` property, not a style) is shown by the window in a `Tooltip` popup (above, flipped below, an arrow at the anchor, no mouse input, the focus untouched) once the mouse has rested `tooltipDelay` (300 ms) on the deepest div with one (`Window::handleMouseMove` follows it, not while a button is down; the delay counts from the next `updatePopups`), at once when another hid less than `tooltipWarmTime` (400 ms) before; a press or a key hides it until the mouse reaches another. By touch, hovering doesn't exist and a long press is the context press (a right button press): the rule is that the context press comes first, and when it opened nothing (no new popup on top of the overlay) the tooltip of what is under the finger shows until the finger lifts; so a div with a context menu never shows its tooltip by touch.
- **Dialogs** (`components/Dialog.hpp`): a modal popup filling the overlay (the `scrim` color) with its `.panel` in the middle (its surface): `.header` (`.icon`, `.title`, a `.close` icon button), `.body` (`.description`, then what is added to `body()`), `.footer` (shown once an `action(label, callback, variant, closes)` is added, after a hairline); `wide(true)` for the 560 px width; a press on the backdrop closes it unless `dismissible(false)`, Escape always; it focuses its panel (no ring until Tab), traps Tab and gives the focus back.
- **Toasts** (`components/Toast.hpp`): `Window::toast(ToastOptions)` adds a `Toast` (title, description, `ToastVariant` `Info`, `Success`, `Warning` or `Danger` as a class and the icon's tile, actions, a close button) to the window's `ToastStack` (`Window::toasts()`, a non-modal popup in the bottom right corner that Escape and outside presses leave alone), the newest at the bottom, at most `ToastStack::limit` (3, the oldest goes). Each closes after its `timeout` (5 s; 0 keeps it), counted by `updatePopups` and held while the mouse is over the stack, or when an action (unless `keepOpen`) or the close button is clicked (`dismissed`).
- **Window dragging**: `Window::addDragArea(div)` (`TitleBar` and the `AppShell` sidebar's header register themselves) and `Window::isDragArea(x, y)`, which SDL's hit test asks before a press is delivered, so the window manager or compositor moves the window (on Wayland too). `startDrag()`/`stopDrag()` remain as the fallback where there's no hit testing; `Window::supportsDrag()` is false where neither works (GLFW on Wayland).
- **Style system** (`psychic-ui/style/`): `StyleManager` holds selector→`StyleDeclaration` rules (descendant selectors on tags and `.class`es, matched case-insensitively), fonts, the theme and the skin set. The cascade follows CSS: matching rules apply by weight (specificity), and on equal weight the rule declared last wins (rules are kept in declaration order). Rules are indexed by what their rightmost part requires (id, else first class, else tag), so a Div is only tested against the rules indexed under its own id, classes and tags, plus the pseudo-class-only ones. An unparsable selector throws `std::invalid_argument`. `reset()` empties the rules but keeps them allocated, so a `Style &` from `style()` never dangles; a rule declared again starts empty, after the others. A `StyleSheet` subclass implements `load(StyleManager*)`, writing its rules from `manager->theme()`. Windows apply them with `loadStyleSheet<T>(reset)`, and loading several stacks them over the skin set's rules (e.g. `DemoStyleSheet`); the style manager keeps them, in load order (a type loaded again runs again in its place). Each `Div` gets a computed `Style` (`computeStyle`: the `*` rule, then what it inherits from its parent, the matching rules, its inline style, and its `_defaultStyle` for what's still unset). `styleUpdated()` is the hook for reacting to it; it must assign derived state from the computed value or its default every time, so that a rule that stops matching (`:hover`, a removed class) takes its effect away. Some properties are inherited down the tree (`inheritedProperties()`, a mask; skins inherit almost everything from their component).
- **Style properties are defined once**, in the `PSYCHIC_UI_STYLE_PROPERTIES` X-macro of `style/Properties.hpp`: name, stored type, setter argument type, default, inherited or not, layout (read by Yoga) or paint-only. It generates the `Property` enum, the flat `StyleValues` struct, the inherited/layout/paint masks, and `Style`'s typed getter and chainable setter for each (`manager->style("Button").padding(12).cursor(Cursor::Hand)`, `computedStyle().fontSize()`). A `Style` is that struct plus a `std::bitset` of which properties are set: copying, overlaying and comparing never allocate, and `diff` gives the changed mask, from which `Div::updateLayout` pushes only the changed layout properties to Yoga (paint-only changes never touch it). To add a property: add its line to the table; if it is a layout property, push it in `Div::updateLayout` (Div.cpp); otherwise read it where it is drawn. `hitSlop` (window units, not inherited, paint-only) widens where presses reach a div without changing its look: a press that lands on nothing taking presses (no button, press, release, click or context menu subscriber on its hit path) goes to the div with a slop reaching it whose center is nearest, moved onto its edge (`Window::handleMouseButtonChange`, `hitSlopTarget`); it applies in every mode, and the skin sets give it a value only in touch density. `gap` (and `rowGap`/`columnGap`) is Yoga's gap between children; `HBox`/`VBox` (`components/Box.hpp`) are just presets for `direction` and `gap` in the default style.
- **Style values** (`style/Values.hpp`) are typed, so mistakes don't compile: `Length` (a number is pixels, `50_pct` is percent 0-100 like CSS, `Auto`; the literals are in the inline namespace `psychic_ui::literals`), scoped enums for every enumerated property (`Direction` is the flex axis, `TextDirection` is ltr/rtl, `Justify`, `Align`, `Position`, `Wrap`, `Overflow`, `Display`, `BoxSizing`, `TextAlign`, `Cursor`, `Orientation`), `Color` (only from `rgb(0xRRGGBB)`, `argb(0xAARRGGBB)`, `Color::fromARGB` or a psychic-color color; `.argb()` gives Skia's `SkColor`), and `Atom` (interned strings) for the open sets, font family and skin name. The setters' argument wrappers (`detail::BoolArg`, `FloatArg`, `StringArg`) reject `"false"` for a bool, `0` for a string and a bool for a number. `themes/palette.hpp` has named colors in `psychic_ui::palette`.
- **Themes** (`psychic-ui/themes/`): a `Theme` (`Theme.hpp`) is values only: its `name`, its `scheme` (`ColorScheme::Light` or `Dark`), and four groups, on Pivotal's token roles (`packages/ui/src/styles/tokens.css`): `Palette` (layers `base`, `surface`, `raised`, `overlay`, `frame` (the app frame), `page` (the inset page panel), `hover`; hairlines `line`, `lineStrong`; text `text`, `textSecondary`, `textMuted`; `accent`, `accentHover`, `accentText`, `accentSoft`, `onAccent`; `danger`, `dangerText`, `warning`, `warningText`, `success`; `scrollThumb`, `scrollThumbHover`, `scrim`, `switchOff`), `Elevation` (`Shadow`s: the two-layer `overlay` + `overlayContact`, and `thumb`), `Typography` (the three fonts, and Pivotal's scale as `TextStep`s of size and leading: `xxs` 10/14, `xs` 11/16, `sm` 12/18 (body), `base` 13/20 (inputs, menu rows), `md` 14/20, `xl` 18/26, `xxl` 20/28) and `Metrics` (`Radii` by role: control 8, button 999 (pills), surface 12, popup 16, row 8, page 16, check 4, small 6; border, focus ring 2 offset 1, the 4 px spacing scale `space(n)` named like Pivotal's `--space-n`, gutters, the frame inset 8, bars 44 and 52, the sidebar's and a menu's widths, thin scroll bars, icon sizes and stroke; and the `Sizes` that follow the density: `pointer` and `touch` values for `controlXs`/`Sm`/`Md` (20, 24, 28), `rowSm`/`Md` (32, 40), `textStep` and `hitSlop`). The named ones are `constexpr`: `themes::pivotalDark` and `themes::pivotalLight` (`pivotal.hpp`, Pivotal's tokens value for value with its `color-mix`es precomputed; the default skin set's), `themes::oneDark`, `themes::oneLight` and `themes::psychic` (their colors on the same roles, in Ubuntu); groups mix with designated initializers. `StyleManager::theme(t)` (or `Window::theme(t)`) stores it, clears the rules (fonts and skins stay) and loads every kept stylesheet again in order, so app sheets that read the theme follow it and their rules still win; rules declared outside a stylesheet are dropped (`Window::theme` recreates the runtime ones, `createStyles`). The style manager's `density()` (`Density::Pointer` or `Touch`) picks the sizes stylesheets read with `manager->sizes()`; switching it replays the stylesheets the same way, which a window does when it enters or leaves touch mode (a new window starts at the pointer density; the manager is shared, so the last window to switch decides). The default skin set's sizes are the same in both densities except the hit slop (0 with a pointer, 10 by touch, so a 24 px control reaches 44 px), so nothing looks different by touch. A new style manager starts with Pivotal Dark.
- **Component/Skin split**: `Component<SkinT>` (`Component.hpp`) is a `Div` whose visuals come from a skin child implementing `SkinT`, the component's skin interface (`ButtonSkin` in `components/Button.hpp`, `RangeSkin` in `Range.hpp`...). The skin is always child 0 and draws the component; the component's own `draw` is a no-op and it ignores internal layout constraints: its padding, border and content layout (`direction`, `justify`, `align*`, `wrap`, `gap`) aren't pushed to its own Yoga node but inherited by its skin, which grows to fill it. Skins come from the style manager's **skin set** (`skins/SkinSet.hpp`, decisions D2, D3, D5, D9): a `SkinSet` is a `StyleSheet` that also registers a skin per interface and variant in a typed `SkinRegistry` (`skins.add<ButtonSkin, DefaultButtonSkin>()`, `.add<ButtonSkin, DefaultBasicButtonSkin>("basic")`), names its `defaultTheme()` and may name a `fallback()` set for what it lacks (its skins and rules go first, under the set's). `window.skinSet<DefaultSkins>()` (or `StyleManager::skinSet<S>()`, or `loadStyleSheet<S>()`) installs one per style manager, with its default theme, and bumps `skinsGeneration()`; `Component::styleUpdated` hatches `styleManager()->skin<SkinT>(variant)` when the `skin` style property (the variant name, "" for the default) or the generation changes: the variant from the set or its fallbacks, else the interface's default, so never no skin once a set is in use. `.skin(std::make_shared<MySkin>())` sets one by hand, kept until the property or the set changes. On a re-hatch the old skin's `removedFromComponent` and the new one's `addedToComponent` move what the component owns (a `TextInput`'s text display, a `TextArea`'s scroller), so it keeps its text. `skins/` holds `paint/` (stateless primitives: `paint::Box::of(div)` is a div's border box as an `SkRRect` from its computed radius and border, `fill`, `stroke`, `arrow`, `disc`, `circle`), `base/` (one base per interface, which creates the **parts contract**, the class names app rules can target with any set: `Button .icon` (`Button::icon(name)`, not displayed without one), `.label` (not displayed when empty); `CheckBox .box`, `.label` (and the check box's `checked` class); `ScrollBar .track`, `.thumb`; `Range .track` with `.fill` (from the start, or the bottom, to the value) and `.thumb` (centered on the value) inside it, then `.value`, and the skin's `.horizontal`/`.vertical`, the base placing the fill and the thumb and answering `valueAt` along the track; `MenuButton .check` (displayed in menus with checkable rows), `.icon` (`MenuItem::icon`, displayed in menus with icons), `.label`, `.shortcut`, `.indicator` (the check after the label, in a select's list), a submenu's `.arrow`, and the row's `checked` and `danger` classes; and calls one `drawChrome(canvas, box, SkinState)` hook from `draw`). Skins only draw and say where things are (decision D4): components own the input, so a new look never reimplements it. `Range` handles presses and drags and asks its skin `valueAt(x, y)` (the linear value at a point), `ScrollBar` drags the thumb from its skin's `trackRect()` and `thumbRect()`, and one directory per set: `default/` is `DefaultSkins`, its skins, which only paint, and their rules.
- **The default skin set is Pivotal's design system** (P1 Faithful, decided on `.lavish/design-system-options.html`), drawn from the theme: buttons are pills (28 px, 12 px medium text, 10 px sides), secondary by default (raised, in a hairline), with skin variants as classes on `DefaultButtonSkin` (`button.skin("primary")`, `"ghost"`, `"quiet"`, `"danger"`; `"tab"` is `DefaultTabButtonSkin`, underlined in its `borderColor`; `"basic"` and `"title-bar"` remain), `.small` (24 px) and `.icon-button` (a 24 px square) classes; a 14 px check box, the accent filling it with a check icon when checked; the slider a 4 px track in the strong hairline, the accent's fill, a 14 px thumb in `onAccent` with the thumb shadow, the value after it; raised text fields in a hairline, the accent's border when focused (no ring, as Pivotal); thin translucent scroll thumbs; menus on the overlay color, a strong hairline, the popup radius and the two-layer overlay shadow, with 32 px rows raised when highlighted, icons, check marks in the primary color, muted shortcuts, a chevron for submenus, danger rows in the danger color tinted when highlighted, disabled rows at 45%, hairline separators across the menu and small muted group labels; selects as raised fields like text inputs with a muted chevron, the accent's border while open or focused by the keyboard; tooltips as 11 px labels on the overlay color in a strong hairline (radius 8, the overlay shadow) with an arrow; dialogs on the `scrim`, the panel 400 px (560 wide) on the floating surface, 16 px gutters, the title in 12 px regular, the muted description, the footer after a hairline with the actions at the end; toasts 352 px on the floating surface, 16 px from the corner, the icon on a 24 px tile in the variant's soft color, the title medium, the description secondary, 20 px action buttons; ghost menu bar triggers, quiet tool bar buttons in a 44 px band, tabs underlined in the text color; window controls (`WindowControls`, the three buttons a `TitleBar` holds) as 11 px dots, grey (the strong hairline) at rest and in the theme's danger, warning and success colors while the pointer is over the group (`WindowControls:hover`), as macOS's. Every focusable control shows Pivotal's focus ring on `:focus-visible` (`outline*`: 2 px accent, 1 px out). Text has three levels (`TextRole`, `role(TextRole::Secondary)`: the `text-primary`, `text-secondary` and `text-tertiary` classes) and `.h1` to `.h6` headings.
- **The app frame** (`components/AppShell.hpp`, `Sidebar.hpp`): `AppShell` is Pivotal's frame, a `Sidebar` the window's full height and the page beside it (`page()`, a panel inset by the frame inset, rounded, clipping, in `page` over the `frame` color). The sidebar's `SidebarHeader` holds the window controls and the app's mark and name (`sidebar.title("…").mark("P")`) and is the window's drag area; `section(heading)` adds a `SidebarSection` (sections after the first are set apart by a hairline), whose `item(label, icon)` adds a `SidebarItem` (an icon, a label, a `count`). One item is current (`current` class: raised, its icon in the accent; `Sidebar::select`, `current()`, `onChange`/`changed`); `selectable(false)` makes an item act (`onClick`) without becoming current; items take the focus, Up and Down move along them, Enter or Space picks one. `PageHeader` is a page's title bar (icon and title, then what is added to it), the sidebar header's height so that their lines meet. A set's rules may also target its own skins' tags (`Button DefaultButtonSkin`), which binds them to that set. Widgets are in `psychic-ui/components/`.
- **Lists** (`components/Rows.hpp`, `List.hpp`, `DataGrid.hpp`, `Tree.hpp`): `List`, `DataGrid` and `Tree` are `RowGroup`s, with a single selection among their `SelectableRow` descendants (the `selected` class; `select(row)` or `select(index)`, `selection()`, `selectedIndex()`; a click selects) and the keyboard: one row is in the Tab order (the selection, else the first), Up, Down, Home and End move the focus and the selection and scroll the row into view in its nearest scrolling ancestor, Space selects the focused row; keys reach the group because the window gives them to the deepest subscriber on the focus path. Their event is `onSelectionChange`/`selectionChanged` (typed: `ListRow *`, `DataGridRow *`, `TreeNode *`), not `onSelect`/`selected`, which is the rows' state getter. `ListRow` has parts made when first set: `.leading` (`icon(name)`, `avatar(name)`), `.text` (`.title`, `.secondary`), `.trailing` (`meta(text)`, anything added to `trailing()`). `DataGrid`: `columns({{"Name"}, {.title = "Size", .width = 80, .align = TextAlign::End}})` (0 shares what is left), `row({values})`; a `.header` row over a `.body` that scrolls under it (sticky by construction) with an overlaid scroll bar; a sortable column's header holds a `.sort` button (title and `.sort-icon` arrow) that cycles ascending, descending and the order rows were added in (`sort(column, SortOrder)`, `onSortChange`/`sortChanged`); sorting compares cells' text, as numbers when both start with one, and moves the rows (`RowGroup::reorder`) keeping the selection and the focus. `Tree`: `node(label, icon)` on the tree or a `TreeNode`, a `TreeRow` (`.indent` a step per level, `Tree::indent`, the `.disclosure` chevron whose column leaves keep, `.icon`, `.label`, `.trailing`) over the `.children`; `expanded(bool)`/`toggle()`, `onExpansionChange`/`expansionChanged(node, expanded)`; Right expands or goes to the first child, Left collapses or goes to the parent, Enter toggles, as WAI-ARIA's tree view; collapsing a node that holds the selection selects it. `Inspector`: a `.heading` (`title(t, subtitle)`, `icon`), `section(title)` of `InspectorField`s (`field(label, text)`: `.name` 104 px, then `.value`, which holds controls too). Smaller pieces: `Badge(label, Tone)` (the `small` class is 16 px), `StatusDot(Tone)`, `Chip` (a focusable pill: `icon`, `selected`, `removable` shows a `.remove` x; the x, Backspace or Delete emit `onDismiss`/`dismissed`, since `removed()` is the hierarchy's), `Kbd("⌘ K")` (a `.key` cap per space-separated key), `EmptyState(icon, title, description)` with `action(label)`, a primary button. `Tone` (`components/Tone.hpp`: `Neutral`, `Accent`, `Success`, `Warning`, `Danger`) is a class on its component (`Badge.success`). `Avatar(name)` is a `Component<AvatarSkin>` (`skins/base/AvatarSkinBase`, parts `.initials` and `.status`, a StatusDot): Pivotal's initials (`Avatar::initialsOf`), `size(AvatarSize::Large)` (16, 20, 24, 32 px as classes `xs` to `lg`), `status(Tone)`, and `colorful(true)`, which `DefaultAvatarSkin` tints with a hue picked from the name around the accent's. Everything else is rules in `DefaultSkins` (Pivotal's lists: 48 px rows between hairlines, `.md` 40 and `.sm` 32; the selection raised with a 2 px accent bar, a left border transparent until then; tree rows as the sidebar's).
- **Inputs** (`components/SearchField.hpp`, `Switch.hpp`, `SegmentedControl.hpp`, `NumberStepper.hpp`, `ColorSwatches.hpp`; base skins in `skins/base/`, the default ones in `skins/default/DefaultInputSkins.hpp`), Pivotal's, each taking the focus with a `:focus-visible` ring (the fields an accent border instead) and hit slop by touch. `TextInput::placeholder("…")` shows the skin's `.placeholder` part while empty. `SearchField`: the `.icon`, its `.input` (a bare TextInput) and a `.clear` button while it has text; Escape clears, Enter emits `onSubmit`/`submitted`, `onChange` the text. `Switch` (`checked()`, `.checked` class; parts `.track`, `.thumb`, `.label`): a click, Space or Enter flips it, the thumb drags (past `dragThreshold`) and lands on the nearer side; the skin places the thumb by flex-growing the space around it and answers `positionAt(x, y)`; there is no animation mechanism, so it moves instantly. `SegmentedControl` (`segments({{"Day"}, {"", "sun"}})`, `selected()`; parts `.segment` with `.icon`/`.label`, `.selected`): a radio group, the arrows, Home and End move the selection, the skin answers `segmentAt`. `NumberStepper` (`value()`, `range`, `step`, `decimals`; parts `.decrement`, `.value`, `.increment`, owned by the component): the buttons (disabled at the bounds), Up/Down (Shift ×10) and the wheel while focused step it, typed text is set on Enter or blur, Escape reverts; no press-and-hold repeat (no timer). `ColorSwatches` (`colors`, `selected()`, `value()` a `Color`; Pivotal's palette by default): `.swatch` chips wrapping into a grid, the selected one ringed in the text color (the accent with the focus), the arrows move it, the skin answers `swatchAt` (the nearest chip).
- **Signals** (`psychic-ui/signals/`): header-only `Signal`/`Slot`/`Observer`. `Div` is an `Observer`, so its subscriptions are torn down with it.
- **Events** follow one convention: a chainable connector `on` + a verb in the present tense, and the `Signal` member it subscribes to, named with the same verb in the past tense: `onClick`/`clicked`, `onDoubleClick`/`doubleClicked`, `onMousePress`/`mousePressed`, `onMouseRelease`/`mouseReleased`, `onMouseReleaseOutside`/`mouseReleasedOutside`, `onMouseButtonChange`/`mouseButtonChanged` (press or release), `onMouseMove`/`mouseMoved`, `onMouseEnter`/`mouseEntered`, `onMouseExit`/`mouseExited`, `onMouseScroll`/`mouseScrolled`, `onContextMenuRequest`/`contextMenuRequested`, `onKeyPress`/`keyPressed`, `onKeyRepeat`/`keyRepeated`, `onKeyRelease`/`keyReleased`, `onType`/`typed`, `onFocus`/`focused`, `onBlur`/`blurred`, `onScroll`/`scrolled`, `onResize`/`resized`; components add `onChange`/`changed`, `Text` `onSelectionChange`/`selectionChanged` and `onCaretMove`/`caretMoved`, `Window` `onMenuOpen`/`menuOpened`, `onMenuClose`/`menuClosed` and `onInputModeChange`/`inputModeChanged`. A new event follows the same rule. Connectors are declared with `PSYCHIC_UI_EVENT(connector, signal)`, which subscribes for the Div's lifetime and returns `Self &`. Use the signal itself (`button.clicked.subscribe(...)`, kept in a `ScopedSlot`) to stop listening early, and `subscribeTo` to listen to something that may die first. Callbacks capture `this` or raw pointers, never a `shared_ptr` to the Div that owns the signal (a cycle that leaks). Whether a div has the focus is `hasFocus()`. A `Signal` also takes a callback with no parameters, which ignores its arguments (`onClick([] { ... })`). Every mouse signal passes one `const MouseEvent &` (`psychic-ui.hpp`, a plain aggregate): `x`/`y` in the receiving div's content coordinates (from its top-left corner, plus its scroll offset, as before), `windowX`/`windowY`, the `button` that changed (`NONE` for moves and scrolls), `down` (for `mouseButtonChanged`), the `buttons` held after the change, `modifiers`, `clickCount` (1, 2, 3... for presses in a row of one button, kept for their release and click; 0 when no press made it: moves, scrolls, and clicks or context menus from the keyboard), `source` (`InputMode`: `Touch` for the window's touch gestures, `Pen`) and `scrollX`/`scrollY`. `mouseEntered`/`mouseExited` pass the move that entered or left, so a hover from a finger can be told apart. The backends fill it in window coordinates; the window adds `windowX`/`windowY`, `buttons` and, when the backend leaves it 0, `clickCount` (SDL gives its own, from the system's settings; GLFW's and pens' presses are counted within `multiClickDelay`, 500 ms, and `multiClickDistance`, 4 px; taps on the touch clock within twice `touchSlop`). `contextMenuRequested` asks for a context menu: on a right button press (as on macOS and Linux; Windows waits for the release), so also a touch long press and a pen's barrel button, after `mousePressed`, and from the Menu key or Shift+F10 on the focused div, at its center, before the keys reach `keyPressed`; the deepest div with a subscriber on the hit or focus path gets it, once. `Button` and `SidebarItem` clicked by Enter or Space emit `clicked` at their center (`Div::mouseEventAtCenter()`). The virtual dispatch methods the window and backends call use the same verb, `handle` + the connector's verb, and take the event in the parent's coordinates: `handleClick`, `handleMousePress`, `handleMouseButtonChange`, `handleMouseMove`, `handleContextMenuRequest`, `handleKeyPress`, `handleType`, ... A press that starts on a Div ends there: `mouseReleased` fires once per release, after `mouseReleasedOutside` when released outside. `clicked` and `doubleClicked` are left button only (so a touch tap clicks and a long press doesn't); the press, release and button change signals report every button. A div with a `clicked` subscriber swallows left presses, so a parent's `mousePressed` doesn't take them; `Button` looks pressed for the left button only.
- **Text**: `TextBase` plus `utils/TextLayout` back `Text`, `Label`, `TextInput` and `TextArea`. `TextLayout` wraps SkParagraph (shaping, bidi, font fallback, wrapping, alignment) and answers what editing asks: lines, caret positions, hit testing, and word and sentence boundaries (ICU break iterators); indices are UTF-16, like the `icu::UnicodeString` that `Text` edits. Every line is exactly the line height (a forced strut, half-leading). Text with subpixel positioning (the default) is hinted slightly, which keeps linear advances; normal hinting rounds advances to whole pixels and crowds small text, so it's only used without subpixel positioning (`fontHinting()`). Fonts come from `StyleManager::fontCollection()`: the loaded fonts by name (a `TypefaceFontProvider`), then the system's, which also fill in missing characters. Measuring (`maxContentWidth`, `lineCountAt`) lays the paragraph out at other widths without disturbing the layout used for painting.
- **Icons** (`psychic-ui/icons/`): vector icons as data, an `IconDefinition` (name, square grid, elements of SVG path data, each stroked or filled; `IconSet.hpp`). `IconRegistry::shared()` holds the bundled sets, then what the application `add`s (same name replaces); each icon's path data is parsed once with `SkParsePath::FromSVGString`, on first draw, and its `SkPath`s kept. An unknown name, or data that doesn't parse, draws nothing and is reported once on stderr. Two ways to draw one: the `Icon` component (`components/Icon.hpp`, a measured Div: `add<Icon>("search").size(20)`, `name("x")` changes it), and, inside skins, `paint::icon(canvas, name, rect, color, strokeWidth)` (`skins/paint/Icon.hpp`). Both draw in `color`, the grid filling a square whose corner is snapped to a device pixel (when the canvas only scales and translates), with round caps and joins. Two inherited style properties: `iconSize` (default 14, Pivotal's medium) and `iconStrokeWidth`, in units of a 16-unit grid whatever the icon's grid (default 1.3, Pivotal's `--icon-stroke`), so every icon has the same weight at a given size. The bundled tables are generated by `tools/icons/generate.py`, never edited by hand: `PivotalIcons.cpp` from Pivotal's `packages/ui/src/icons/icons.tsx` (`generate.py pivotal <icons.tsx>`; 16-unit grid; names are its component names in kebab case without `Icon`, and `StarIcon`'s filled form is `star-filled`), then `LucideIcons.cpp`, the Lucide icons Pivotal's set lacks, under Lucide's names (`generate.py lucide`: the names listed in `tools/icons/lucide.txt`, from lucide-static 1.64.0, which the script downloads from npm at generation time, never at build time, and checks against its pinned npm integrity hash; `--package <dir>` reads an extracted one instead; it refuses a name Pivotal's set has). Lucide is ISC (some icons MIT, from Feather): the license is in the generated file's header and in full in `psychic-ui/icons/LICENSE-Lucide.txt`. To add a Lucide icon, add its name to `lucide.txt` and run the script. Normalization: each set's grid fills the icon's box (Pivotal 16 units, Lucide 24, whose glyphs cover about the same share of their grid), and strokes take one weight from `iconStrokeWidth`: Pivotal's own 1.3/16, which is within 3% of Lucide's 2/24.
- `lib/psychic-color` is the author's own color library (submodule), used for theme colors.
- `extlib/rxcpp` exists but is not wired into the root build.

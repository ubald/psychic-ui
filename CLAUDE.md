# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Status

The project is being resumed after years idle; its website is published from this repository (see Executables). Yoga (3.2.2), SDL3, GLFW and Skia (m159) are current.

## Building

The toolchain and system libraries come from the Nix flake's dev shell (`flake.nix`), loaded by direnv (`.envrc`: `use flake`); outside direnv, prefix commands with `nix develop -c`. The flake is a convenience for local development only: the build must also work without Nix, so never make a dependency reachable only through it. Yoga, Skia and `lib/psychic-color` are git submodules; CMake stops with a fatal error if they are missing. SDL3 and GLFW come from `find_package` (`SDL3 3.2`, `glfw3 3.4`, both in the flake), otherwise FetchContent downloads a pinned release (SDL 3.4.20, GLFW 3.5.1, by URL and SHA-256) and builds it static: SDL3 without audio, joystick, haptics, sensors, camera, GPU, render, Vulkan or the X11 extensions it would otherwise stop on when their headers are missing (XScrnSaver, XShape, XTest, Xdbe), GLFW with Wayland only when its development files are found and SDL3 isn't fetched too (both static, their generated Wayland protocol symbols would clash). `-DCMAKE_DISABLE_FIND_PACKAGE_SDL3=ON -DCMAKE_DISABLE_FIND_PACKAGE_glfw3=ON` forces the downloads. `CMakePresets.json` has `debug` and `release` presets that build in `build/<preset>` and export `compile_commands.json` (and `asan`, see Tests):

```sh
git submodule update --init --recursive
cmake --preset debug
cmake --build --preset debug -j"$(nproc)"
```

No preset but `windows` sets a generator, so it stays CMake's default (Make), not Ninja; pass `-j` yourself.

- CMake 3.24 or newer.
- Everything is a target: psychic-color is the static `psychic-color::psychic-color`, Yoga is its own static `yogacore` target, linked PRIVATE (no public header includes Yoga: `Div.hpp` only forward-declares `YGNode`; measurable divs override `Size measure(Constraint width, Constraint height)` from `Measure.hpp`, with `Fit::Exact`, `AtMost` or `Unbounded`, converted from Yoga in `Div.cpp`; the tests link `yogacore` themselves to inspect nodes) (`extlib/external/yoga/yoga/CMakeLists.txt`, added from `extlib/yoga/`; it compiles as C++20 with `-Wall -Werror` in its own directory), Skia the imported `Skia::Skia`, SDL3 `SDL3::SDL3`, GLFW `glfw`. ICU and Fontconfig use CMake's own Find modules; there's no `cmake/` directory any more. On macOS the Homebrew prefix comes from `brew --prefix`.
- Skia (`chrome/m159`) is built by CMake, which runs `gn gen` then `ninja` for those targets as the `skia-build` custom command when one of its static libraries (`libskia.a`, `libskparagraph.a`, `libskshaper.a`, `libskunicode_icu.a`, `libskunicode_core.a`, `libskcms.a` in `<build dir>/extlib/skia/build`) is missing, with Python 3 for gn's scripts and nothing written into Skia's checkout. Ninja is required when Skia is built here (`find_program ... REQUIRED`, not with `PSYCHIC_UI_SKIA_DIR`; the flake, both CI jobs and Visual Studio's Build Tools have it). The gn Skia pins is downloaded at configure time (needs network) into `<build dir>/extlib/skia/gn/`, by `file(DOWNLOAD)` with a SHA-256 per platform (`linux-amd64`, `linux-arm64`, `mac-amd64`, `mac-arm64`, `windows-amd64`; another host is a fatal error) from the revision of Skia's `bin/fetch-gn` (update both together when Skia moves); the downloaded `gn` binary runs through nix-ld. On Windows another compiler than clang-cl (MSVC's `cl`) stops configure with a fatal error when Skia is built here (gn would build it with `cl` and fail deep in ninja). The gn args are written at configure time (they are in `extlib/skia/CMakeLists.txt`, with the compilers CMake uses (`cc`/`cxx`) outside Windows), one per line, to `<Skia output>/args.gn` (only when they change, so its timestamp stays; never into a given `PSYCHIC_UI_SKIA_DIR`), which `gn gen` reads with the Python CMake found (`--script-executable`). No `git-sync-deps`: every third-party library Skia uses comes from the system (ICU, HarfBuzz, FreeType and Fontconfig on Linux; ICU, HarfBuzz and CoreText on macOS; ICU and HarfBuzz from vcpkg and DirectWrite on Windows), and image codecs, PDF, SVG, Skottie, Graphite, Vulkan, Metal and Skia's own GL loaders are off. The first Skia build is slow; `-DPSYCHIC_UI_SKIA_DIR=<dir>` (cache `PATH`, empty by default; `PSYCHIC_UI_SKIA_OUTPUT` is the directory in use) links from `<dir>` instead, a prebuilt Skia that the build only reads: it must already hold the libraries (configure stops with a fatal error naming a missing one; build `skia-build` in a build directory without `PSYCHIC_UI_SKIA_DIR` and point at its `extlib/skia/build`), they are no custom command's outputs then, so no clean deletes them, and `skia-build` is a target that does nothing. Use one directory per compiler and platform.
- `Skia::Skia` is an interface target over those libraries: Skia's source root as include directory (`#include "include/core/SkCanvas.h"`, `"modules/skparagraph/include/Paragraph.h"`), the public defines of the configuration it was built with (`SK_RELEASE`, `SK_GANESH`, `SK_GL`, the shaper, unicode and paragraph ones; keep them in step with the gn args, `gn desc <out> //:skia defines` lists them), HarfBuzz, ICU, and FreeType and Fontconfig, the Apple frameworks or the Windows libraries Skia uses.
- CI (`.github/workflows/ci.yml`, GitHub Actions) proves the build works without Nix, from system packages: Linux on `ubuntu-24.04` (it has no SDL3 or GLFW 3.4, so they're fetched, with their X11/Wayland development packages installed; its default GCC 13 lacks C++23 deducing this, so the job installs `g++-14` and passes it to CMake, which passes it on to Skia's gn), and macOS; both jobs are required. Both cache Skia's output directory per Skia commit and `extlib/skia/CMakeLists.txt`.
- The library requires C++23 (`target_compile_features(psychic-ui PUBLIC cxx_std_23)`), so whatever links it builds as C++23 too: the chainable API uses explicit object parameters ("deducing this"), which need GCC 14+, Clang 18+, Apple Clang 16+ or MSVC 17.2+. The root `CMakeLists.txt` stops at configure time with an older compiler, which would otherwise accept `-std=c++23` and fail deep in the headers.
- CMake options: `PSYCHIC_UI_SHARED` builds psychic-ui as a shared library, else static (Yoga, psychic-color and a fetched SDL3, GLFW or Catch2 stay static either way); nothing sets the cache's `BUILD_SHARED_LIBS`, so a parent project's choice is its own; on Windows `PSYCHIC_UI_SHARED` defaults to `OFF` and `ON` stops configure with a fatal error (the library exports no symbols yet). The library's warnings are `/W4` with an MSVC-style compiler driver (`CMAKE_CXX_COMPILER_FRONTEND_VARIANT`, clang-cl too), else `-Wall -Wextra`. `PSYCHIC_UI_SHARED`, `PSYCHIC_UI_BUILD_TESTS`, `PSYCHIC_UI_BUILD_EXAMPLE`, `PSYCHIC_UI_BUILD_PLAYGROUND` and `PSYCHIC_UI_BUILD_SHOWCASE` default to `PROJECT_IS_TOP_LEVEL`, so a parent project that `add_subdirectory`s psychic-ui gets a static library and none of the extras, no CPack, no `doc` target and no feature summary; it links `psychic-ui::psychic-ui`. `PSYCHIC_UI_BUILD_SDL3` (the runner and the SDL adapter; the demo and playground need it) and `PSYCHIC_UI_BUILD_GLFW_ADAPTER` are `ON` by default.
- Windows builds with clang-cl (for Skia and everything else; MSVC's `cl` is not a goal) from Visual Studio's Build Tools 2026 with the "Desktop development with C++" workload and "C++ Clang tools for Windows" (they bring CMake, Ninja, vcpkg and the Windows SDK), plus Python 3 (`winget install Python.Python.3.13`; the `python.exe` in `WindowsApps` is the Store's stub). From a Developer prompt (`vcvars64.bat`, which sets `VCPKG_ROOT` and `VCINSTALLDIR`): `cmake --preset windows`, `cmake --build --preset windows`, `ctest --preset windows`. The `windows` preset (only offered on a Windows host) is `debug` with Ninja, `clang-cl` for C and C++, vcpkg's toolchain file and its community triplet `x64-windows-static-md-release`: `vcpkg.json` (with a pinned `builtin-baseline`; other platforms never read it) brings ICU and HarfBuzz as static libraries, release builds only, installed into `<build dir>/vcpkg_installed` on the first configure, so executables need no DLLs beside them (ICU's data, linked in, adds about 30 MB to each). So every target links the release dynamic runtime (`CMAKE_MSVC_RUNTIME_LIBRARY` `MultiThreadedDLL`, in Debug too) and Skia gets `/MD` in its `extra_cflags`: Skia's gn sets no runtime and clang-cl's default is the static one, and an object built against another runtime than its neighbours' fails to link (LNK2038). Skia's gn gets no `cc`/`cxx` there but `clang_win` (the LLVM root holding `bin/clang-cl.exe`) and, from the Developer prompt's environment when it is set, `win_vc`, `win_toolchain_version`, `win_sdk` and `win_sdk_version` (`VCINSTALLDIR`, `VCToolsVersion`, `WindowsSdkDir`, `WindowsSDKVersion`; else gn finds Visual Studio with vswhere and takes the highest versions), so Skia compiles against the same STL and SDK as CMake, and no `extra_ldflags`; its libraries are `skia.lib` and so on, fonts come from DirectWrite (`SkFontMgr_New_DirectWrite`), no FreeType or Fontconfig. The library is static only (`PSYCHIC_UI_SHARED`, below). A project that embeds psychic-ui on Windows lists `icu` and `harfbuzz` in its own `vcpkg.json` (vcpkg only reads the top-level manifest) and uses the release dynamic runtime and a release-only triplet (`x64-windows-static-md-release`: a triplet that builds debug libraries too links `/MDd` ICU and HarfBuzz in Debug next to `/MD` Skia, LNK2038). CLion: a Visual Studio toolchain on the Build Tools, architecture `amd64`, and the `windows` preset enabled in CMake's profiles. CI doesn't build Windows.
- Non-Debug shared builds strip the library after linking; use the `debug` preset when debugging.
- `make doc` generates Doxygen docs when Doxygen is installed; the `doc` target only exists when psychic-ui is the top-level project. It writes `docs/html/`, which git ignores: the API reference isn't committed, `tools/showcase/publish.sh` generates it for the website. The flake has Doxygen; the build doesn't need it.
- **Library sources are listed explicitly in `SOURCE_FILES` in the root `CMakeLists.txt`.** A new `.cpp`/`.hpp` must be added there; test files go in `tests/CMakeLists.txt`.

## Tests

Catch2 v3 into one executable, linked to `Catch2::Catch2WithMain` (there's no `main.cpp`) and registered with CTest. `tests/CMakeLists.txt` uses an installed Catch2 3 when `find_package` finds one (the flake provides `catch2_3`) and it passes a check; otherwise FetchContent downloads `v3.16.1` into `<build dir>/_deps`. The check builds `tests/catch2-check/` with `try_compile` (a project of its own, so the installed Catch2's targets can't clash with the download): it must link a program that stringifies a `std::string_view`, because Catch2's library only defines that `StringMaker` when it was itself compiled as C++17 or newer, while our C++23 build of its headers expects it. Without an installed Catch2 the check project still configures and fails to build (`not_found.cpp` `#error`s a marker), since an error while configuring it would stop ours. The download is built as C++23 (`CMAKE_CXX_STANDARD` set around `FetchContent_MakeAvailable`): Catch2 only asks for C++14, which is what AppleClang (whose default is older) then compiles it as, so the downloaded library lacked that `StringMaker` on macOS and the tests failed to link (GCC 14 defaults to C++17, which hid it on Linux). The configure prints which Catch2 it uses and why; a failed check's output goes to `<build dir>/tests/catch2-check.log`. The result is cached and rerun when the compiler, flags, build type, prefix path, ignored paths or `Catch2_DIR` change. `-DCMAKE_DISABLE_FIND_PACKAGE_Catch2=ON` skips the check and forces the download. `lib/psychic-color`'s own tests (`PSYCHIC_COLOR_BUILD_TESTS`) default off when it isn't the top-level project, so they aren't built here.

`PSYCHIC_UI_TEST_CONSUMER` (for Linux and macOS, as it forwards no vcpkg toolchain, triplet or runtime; off by default, on in the Linux CI job) adds the CTest test `psychic-ui-consumer`: `tests/consumer/run.cmake` (`cmake -D... -P`) configures `tests/consumer/`, a project of its own that sets `BUILD_SHARED_LIBS` on and `add_subdirectory`s the checkout (`-DPSYCHIC_UI_SOURCE_DIR`), in `<build dir>/tests/consumer` with this build's generator, compilers and Skia (`-DPSYCHIC_UI_SKIA_DIR=${PSYCHIC_UI_SKIA_OUTPUT}`, so Skia isn't built again), its cache cleared of `PSYCHIC_UI_*` and `BUILD_SHARED_LIBS` each time (`-U`, so the options' defaults are what it checks); builds it with `cmake --build --parallel` on every logical core; then runs its app; any step that fails fails the test with its output. The consumer's configure stops with a fatal error if psychic-ui built its tests, demo, playground or showcase, isn't a static library, or changed or cached `BUILD_SHARED_LIBS`; its `consumer-app` (`psychic_ui_copy_resources`) runs from `<build dir>/tests/consumer/psychic-ui`, which has no `res/` (so fonts must resolve against the executable's directory), and fails unless the theme's regular font loads from its file (loaded again under a name no system font has, as `tests/text/font_tests.cpp` does, and compared with the default font, since a font that didn't load falls back to the system's) and a posted task ran in `runPosted`. It builds the whole library again (static), so it takes minutes (`TIMEOUT` 1800); turn it back off afterwards to keep `ctest --preset debug` fast.

The backend tests (`tests/backends/`) need no display: a fake `SystemWindow`, SDL3 on its `dummy` video driver fed synthetic events (finger events too, from a made-up touch screen), and GLFW on its null platform with its installed callbacks called directly. Touch gestures are tested with explicit times (`touch_tests.cpp`).

`[!shouldfail]` tests are known bugs, each named after its item in `review-2026-11.md` (the review's checklist): they assert the correct behaviour, so Catch2 counts them as expected failures; remove the tag, and tick the item, in the commit that fixes one. Hidden `[asan]` tests (`tests/asan/`) are use-after-free paths that only AddressSanitizer shows: build the `asan` preset (static, ASan and UBSan, a forced-include shim for Skia's layout; copy `build/debug/extlib/skia/build` into `build/asan/extlib/skia/` first, or configure it with `-DPSYCHIC_UI_SKIA_DIR=<checkout>/build/debug/extlib/skia/build`: the preset's sanitizer flags don't reach Skia's gn build, so the debug build's Skia serves it unchanged) and run them one at a time from `build/asan/tests` with `LSAN_OPTIONS=suppressions=../../../tests/asan/lsan.supp`; the checklist's last section has the details.

Time is the tests' own: they call `Window::updateGestures`, `updatePopups` and `updateAnimations` with explicit `std::chrono` times (what `drawAll` does with the system window's clock), then `updateStylesAndLayout()`; they run posted tasks with `runPosted()` themselves (`tests/backends/post_tests.cpp`); a tween or a transition started after an `updateAnimations` starts at its time (`tests/animation/animation_tests.cpp`). The shared `TestWindow` (`tests/backends/fake_system_window.hpp`) reduces motion, so tests that don't care about motion see end values after a style pass; tests of motion turn it back off. It also asks for context menus on the right button's press on every platform (`contextMenuOnRelease(false)`, which Windows defaults to true); tests of the release turn it on.

```sh
ctest --preset debug                                       # all tests, through CTest
./build/debug/tests/psychic-ui-tests                       # all tests
./build/debug/tests/psychic-ui-tests "[style]"             # by tag
./build/debug/tests/psychic-ui-tests "basic style getter"  # by test name
ctest --preset windows                                     # on Windows, from a Developer prompt
```

## Executables

- `example/` builds `psychic-ui-demo` (SDL3): the demo app, where new components are developed before they move into the library. It is an `AppShell` (`example/demo/DemoWindow.hpp`): the sidebar lists the pages (Controls: Buttons, Ranges, Text Input, Inputs, Lists, Popups; Layout: Typography, Divs, Scroller, Canvas, Motion; Assets: Colors, Icons) and, at the bottom, a Theme item opening a menu of themes (System first); a page shows in the inset panel under a `PageHeader` holding the menus and a tool bar. View → Skin Set (Default, Desk, Float) and View → Theme (System, then the current set's `themes()`) are radio groups that switch live, the menu staying open; the sidebar's Theme item opens the same theme list. The sets are one table in `DemoWindow` (`_skinSets`), so adding one is a line. Icons (`example/demo/Icons.hpp`) shows every registered icon at 14 and 20 px with its name, under Inter samples at 11 to 14 px; Lists (`example/demo/Lists.hpp`) shows every list component, a data grid with an inspector that follows its selection. Popups (`example/demo/Popups.hpp`) shows a menu with every kind of row, a context menu, selects, tooltips, dialogs and toasts, and a Slow motion switch (`animationSpeed(0.1)`) to watch them enter and leave. Canvas (`example/demo/Canvas.hpp`, `CanvasPage`) is the Float board's mini app made of library components and demo rules (`DemoStyleSheet`): the page is a canvas (the `frame` color, a dot grid in `canvasDot`) with panels positioned absolutely over it, the document's name and its layers (`Tree`s) at the top left, an `Inspector` at the top right, a `ToolBar` of square quiet tools centered at the bottom (one current, in the accent, under either set), a stage plot in the middle; they float with the theme's `panel` elevation; `tests/demo/canvas_page_tests.cpp` checks it under both sets and every named theme, with a style manager of its own so the demo's rules stay out of the other tests. Motion (`example/demo/Motion.hpp`) shows pucks moved by inline `left` transitions (eased, Pivotal's curve, two springs, instant: Play twice quickly to see a retarget), one drawn from an `Animated<float>`, a short list whose Shuffle button reorders its rows (`ShuffleList`, through `RowGroup::reorder`) so they slide to their new places (layout transitions), the curves plotted with a dot run by `Div::animate`, the theme's motion tokens, a reduced motion switch and controls to play with. The frame counter keeps the loop drawing every frame while it shows (it requests a frame from `render`), so the demo only idles with `--no-fps`. Arguments: `--skin <default|desk|float>`, `--theme <system|pivotal-dark|pivotal-light|one-dark|one-light|psychic|desk-dark|desk-light|float-light|float-dark>` (a theme's name in kebab case; the skin set applies first, whatever the order), `--density <pointer|touch>` (keeps the window in that input mode, and so the style manager at that density, whatever the mouse does: `DemoWindow::forceInputMode`, for captures of the touch sizes without a touch screen; after the skin set, before the theme), `--page <name>` (as in the sidebar, or in kebab case: `canvas`, `text-input`), `--no-fps` (hides the frame counter, for screenshots, and lets the loop idle), `--reduced-motion` (every duration 0), `--slow-motion` (animations ten times slower, `Window::animationSpeed`), `--open <menu|submenu|context|select|dialog|confirm|toasts|tooltip>` (shows the Popups page with that popup open, for screenshots), `--keys <key,key*n,...>` (presses keys once the other arguments have applied: tab, shift+tab, up, down, left, right, home, end, space, enter, escape; for screenshots of the keyboard's focus), `--scroll <pixels>` (scrolls the page down). It also builds `psychic-ui-glfw-host`, a GLFW application that embeds a Psychic UI window through the GLFW adapter (Escape quits).
- `playground/` builds `psychic-ui-playground` (SDL3), a scratch app.
- `showcase/` builds `psychic-ui-showcase` (`PSYCHIC_UI_BUILD_SHOWCASE`), which captures the website's screenshots: no window, no GL, no display. Each **scene** (`Scene.hpp`: a name, a size, a `Look` of skin set, theme and input mode, a `build` of its UI, a `pose` putting it in the state to show, and for motion a `Sequence` of beats) runs on a `Stage` (`Stage.hpp`): its window opened on a `HeadlessSystemWindow` (sizes, a pixel ratio of 2, a clock the stage sets), each frame advancing that clock by a sixtieth of a second, running `runPosted`, `updateGestures`, `updatePopups`, `updateAnimations` and `updateStylesAndLayout`, then painting with `Window::paint` (the public hook `drawAll` uses too) into a raster `SkSurface`; `settle()` runs frames until nothing moves or waits, `hover` and `key` feed input as a backend would. Nothing reads the real clock, so the same code gives the same bytes. `PngWriter` encodes PNGs without a dependency (Skia's codecs are off): per-row filters, LZ77 and deflate's fixed Huffman codes, RGB when opaque; a sequence becomes an animated PNG whose frames hold only the region that changed, identical frames merged. Each scene gets a style manager of its own (`applyLook`, `Looks.hpp`), the showcase's rules (`ShowcaseStyleSheet`: `.backdrop`, `.panel`, `.field`...) over the skin set's, and `compose::` helpers build panels and fields. Scenes live in `scenes/` by subject (Hero: the demo's Canvas page and the whole demo app, from `example/`'s headers; Controls; Popups; Collections; Foundations: typography, icons, Desk's pointer and touch densities, motion); most are captured once per skin set and scheme (`inEveryLook`: `<scene>-<default|desk|float>-<dark|light>.png`). `psychic-ui-showcase --out <dir> [--scene <name>]...` writes them, `--list` lists them, `--live <name>` opens one in an SDL window to work on it (never part of a capture). `tools/showcase/capture.sh [preset] [--out <dir>] [--scene <name>]...` rebuilds it and captures into `build/<preset>/showcase/captures` or the directory given (about a minute in a debug build), as the `showcase-capture` target does into its build directory. Captures are never committed to the source branches.
- The website's source is `site/`: `index.html`, `assets/` (its CSS and a little JS that swaps the screenshots for the skin set and theme picked) and `.nojekyll` (Jekyll would drop Doxygen's files starting with an underscore). Plain HTML and CSS, no build step. GitHub Pages serves the root of the `gh-pages` branch (https://ubald.github.io/psychic-ui/), which only `tools/showcase/publish.sh [preset]` writes: it captures the showcase into a temporary directory (configuring the preset first when it has no build directory), lays out `site/` at the root, the captures in `showcase/` (where the page looks for them: `showcase/<scene>-<set>-<scheme>.png`) and the API reference in `html/` (the page's API links), generated fresh by Doxygen from the `doc` target's `<build dir>/Doxyfile` read from its standard input with the output directory, `QUIET` and the warnings' log overridden, so nothing is written into the checkout (it stops with an error without Doxygen, and configures the preset again when CMake hadn't found it), and makes that tree the local `gh-pages` as one commit without a parent, through an index of its own (`GIT_INDEX_FILE`, `write-tree`, `commit-tree`, `update-ref`): neither the working tree nor the index changes, and each publish replaces the branch rather than adding to it. It never pushes; it prints `git push --force origin gh-pages`. To preview, `git archive gh-pages` into a scratch directory and serve it (`python3 -m http.server`). A new scene shows on the site once `index.html` names it (`data-scene`).

Relative font paths (the themes' `res/fonts/…`, the demo's `fonts/stan0755.ttf`) resolve against the style manager's `resourceRoot()`, the running executable's directory by default (`executableDirectory()`, `utils/ExecutablePath.hpp`: `/proc/self/exe`, `_NSGetExecutablePath` or `GetModuleFileNameW`; empty when it can't tell, which leaves them relative to the working directory); absolute paths are used as they are. `psychic_ui_copy_resources(<target>)`, a CMake function defined by the root `CMakeLists.txt` (so a parent project that adds psychic-ui can call it too), copies `res/` next to an executable after each build of it (`POST_BUILD` `copy_directory`); the demo, the GLFW host, the playground and the tests call it, and `example/` also copies its `fonts/` next to the demo. So binaries run from any working directory.

Bundled fonts live in `res/fonts/<family>/`, each with its license: Ubuntu (`UFL.txt`) and Inter 4.1 (`OFL.txt`, SIL OFL 1.1), Pivotal's typeface: the hinted static TTFs `Inter-Regular.ttf`, `Inter-Medium.ttf` and `Inter-SemiBold.ttf` from `extras/ttf/` of the official release `Inter-4.1.zip` (github.com/rsms/inter, SHA-256 `9883fdd4a49d4fb66bd8177ba6625ef9a64aa45899767dde3d36aa425756b11e`; its `InterVariable.ttf` and `Inter.ttc` match nixpkgs' `inter` 4.1 byte for byte). A theme's `Typography` names its `regular`, `medium` and `semiBold` fonts: Inter ("Inter", "Inter Medium", "Inter SemiBold") by default, Ubuntu (`themes::ubuntuType`: "Ubuntu Regular", "Ubuntu Medium", "Ubuntu Bold") in the One and Psychic themes. `PivotalSkins` loads both families and the theme's (the style manager loads a name once), so any style can use `fontFamily("Inter")`. The tests load fonts from the sources (`PSYCHIC_UI_TEST_FONTS`, `PSYCHIC_UI_TEST_RES`).

- `SDL_LOGGING=app=debug` makes the SDL3 runner print the video driver, GL renderer, samples, stencil bits, hit testing and pixel density it got.
- SDL picks the video driver (decision D4). Under WSLg it falls back to XWayland by itself (the compositor lacks fifo-v1); `SDL_VIDEO_DRIVER=wayland` forces Wayland, which works too. Nix's Mesa only finds WSL's GPU driver with `LD_LIBRARY_PATH=/usr/lib/wsl/lib` and `GALLIUM_DRIVER=d3d12`, which the dev shell sets when `/usr/lib/wsl/lib` exists; otherwise GL is llvmpipe (software).
- Under Xvfb, unset `WAYLAND_DISPLAY` and point `XDG_RUNTIME_DIR` at an empty directory: otherwise GLFW (and SDL when forced) connects to WSLg's `wayland-0` socket and opens windows on the real display.

## Architecture

Retained-mode UI: **Skia** draws, **Yoga** does flexbox layout, and a CSS-like **style system** drives both. Everything lives in `namespace psychic_ui`.

- **`Div`** (`psychic-ui/Div.hpp`) is the base node, like an HTML div. It owns a Yoga node, children (`std::shared_ptr<Div>`, hence `enable_shared_from_this`), tag and class names, mouse/focus handling and signals. Override `draw(SkCanvas*)` for custom drawing; `render()` recurses over children. `add<T>(args...)` constructs a child and returns `T &`: the parent owns it (keep a raw pointer or reference to it, valid while it is a child); `add(child)` / `add(index, child)` add an existing `shared_ptr` and return it as `T &`. `children()` returns the vector by reference, in document order. The computed style is the only input of its Yoga node (`updateLayout` pushes it); `x()`/`y()`/`getWidth()`/`getHeight()` read the last layout. A component's own defaults go in `_defaultStyle`, which stylesheets override.
- **The API is chainable**: every style property has a setter on `Div` itself, generated from the property table, writing the inline style (`div.padding(24).overflow(Overflow::Scroll)`; read values back from `computedStyle()`, or `style()` for the inline ones), plus helpers (`row()`, `column()`, `size(w, h)`, `style(const Style &)` to overlay a reusable `Style`). Every mutator returns the most derived type through C++23 explicit object parameters ("deducing this"), so base and derived setters chain in any order: `add<Button>("x").enabled(false).toggle(true).padding(24)`. Setters and getters share the bare name (`enabled()` / `enabled(false)`, `text()` / `text("...")`, `selected()`, `checked()`, `value()`, `range(min, max)`...). To add one to a component: `template<class Self> Self &name(this Self &self, Arg value) { static_cast<Component &>(self).updateName(value); return self; }` with the work in a protected non-template `updateName`; an explicit-object function can't be virtual, so a setter that subclasses must react to calls a protected virtual hook (NVI, like `enabled()` → `enabledChanged()`, `text()` → `Text::updateText`). A subclass member with a property's name hides the generated setter: bring it back with a using-declaration (`Component::skin()` does `using Div::skin;`). Bool, string and number arguments use the `detail::*Arg` wrappers so misuse doesn't compile.
- **`Window`** is the root `Div`. `Window::drawAll()` runs each frame in this order: `runPosted` (tasks other threads handed over with `post`), `updateGestures`, `updatePopups` and `updateAnimations` with the system window's `gestureTime()`, then the next two in `updateStylesAndLayout()` (no canvas needed, which is how the tests drive it): styles (the whole tree if the `StyleManager` is invalid, otherwise `updateDirtyStyles`, which follows the `_descendantStyleDirty` flags that `invalidateStyle` sets up the parent chain, visible or not; repeated up to `maxStylePasses` times while `styleUpdated` callbacks invalidate more), then layout if the Yoga root is dirty or the window size changed (`YGNodeCalculateLayout` at `windowWidth()`/`windowHeight()`, which the root, with no size of its own, fills; then `layoutUpdated()`), then the popups' placement (`Overlay::place`) and the styles again (their new places, sides and origins), then the starting classes let go (`Div::startingClass`) and the styles again (their transitions start), then the exits that are over leave (`Div::exit`), then the layout again if anything changed it, then, when a layout ran, the layout transitions (`slideLayout`), then `render()` on the Skia canvas, which only paints: per Div, its shadows (`shadow*`, a blurred copy of its border box outside it, grown or shrunk by `shadowSpread`, like CSS `box-shadow`; `shadow2*` is a second layer under the first, for two-layer elevations), `draw()`, its children (clipped by `overflow`), then its `outline*` (a line `outlineOffset` outside the border box, over the children), so any Div gets a shadow or a focus ring whatever its `draw`; neither is inherited, so a skin doesn't repeat its component's (a Div with `opacity` below 1 draws itself and its children into a `saveLayerAlpha` layer, so the subtree fades as one group like CSS opacity; at 0 it draws nothing). Around all of that comes its paint transform, CSS's `translate`, `scale` and `transform-origin`: `translateX`/`translateY` (a percent is of its border box), `scale` times `scaleX`/`scaleY` about `transformOriginX`/`transformOriginY` (from its border box's corner, a percent of its size, the center by default); paint-only and animatable, never laid out and never hit tested (a press finds a div where its layout puts it, whatever it looks like meanwhile: transforms are for motion, popups entering and leaving, and layout transitions, whose offset adds to the translation). Borders on some sides only (`borderTop`...) are drawn on the div's own edges. `dotGrid*` paints a canvas's dot grid over a div's background, under its children (`dotGridColor`, none while transparent; `dotGridSpacing` apart, the first half a step in from the corner; discs of `dotGridRadius`), clipped to its border box, only the visible dots in one `drawPoints`: a style property rather than a paint primitive, so a skin set's rules can give any div a canvas (Float's `AppShell`) without a skin or a subclass.
- **Focus**: a press focuses the deepest div under it (`Window::requestFocus`), the whole path from the root to it; `:focus` matches a focused div that is `focusEnabled`. A disabled or hidden div doesn't take the focus: when the deepest `focusEnabled` div on the path is one, the path stops at its parent (a press on a disabled field focuses what is around it; a popup closing doesn't give the focus back to a trigger disabled or hidden meanwhile). Tab and Shift+Tab (`Window::focusNext`) move the focus through the divs that take it (focusEnabled, enabled, visible; the topmost popup's that traps the focus, a menu or a dialog, else the app's), in document order, wrapping around; focus moved by the keyboard sets `Window::focusVisible()`, which `:focus-visible` also requires (like CSS's: a ring for the keyboard, none for a click). Buttons, check boxes, ranges and sidebar items take the focus: Space or Enter clicks a button, Space toggles a check box, the arrows, Home and End move a range. Text fields (`TextInput`, `TextArea`, `SearchField`, `NumberStepper`) take it themselves (`TextField`), whatever part of them is pressed, so Tab or a press beside the text lets one type. Skia is set up lazily on the first frame, with a GL interface assembled from the system window's `glProcAddress` (Skia's own GL loaders aren't built); the surface is the framebuffer's pixel size, remade on the frame after a resize, and the canvas is scaled by the pixel ratio. Every Yoga node is created with one shared config (web defaults, rounding disabled), owned by `Div.cpp`. The system window's visibility is `windowVisible()` (`close()` turns it off), separate from the `visible` style, which hides a Div from painting and hit testing but keeps it in the layout.
- **Backends** (`psychic-ui/applications/`): `SystemWindow` (`SystemWindow.hpp`) is the platform side of a `Window`: sizes (window units for input and layout, framebuffer pixels for drawing), GL proc addresses, window operations, drag support, text input, clipboard, the system's light or dark mode (`colorScheme()`, `Unknown` by default, which GLFW keeps). Adapters implement it over a window they don't own and translate its events: `SDL3SystemWindow` (`handleEvent(const SDL_Event &)`, `installHitTest()`) and `GLFWSystemWindow` (installs its callbacks over the host's and chains to them, like Dear ImGui's `imgui_impl_glfw`). `SDL3Application` is the only runner: SDL init, one SDL window and GL context per `Window`, the loop. There is no application interface; embedding hosts have no application object. A system window detaches from its `Window` in its destructor, with its context still current.
- **Frames and idling**: nothing redraws by itself. A window says what it needs: `needsFrame()` (a frame was asked for with `requestFrame()` — the first one, a resize, a visibility change, `Div::scrollTo`, or app code whose `draw` reads something that changed without input —, tasks posted and not run yet, dirty styles, a dirty Yoga root, a new window size, or `animating()`: tweens, transitions or a fling), `nextFrameTime()` (the soonest timer on the `gestureTime()` clock: a tooltip's delay, its warm time, a toast's timeout, a long press; "now" for one that starts counting with the next frame) and `untilNextFrame(now)` (zero, the time to that timer, or nullopt: only input can change anything). `requestFrame()` may come from another thread: the first one after a frame calls `SystemWindow::wake()`, which pushes an SDL user event (`SDL3SystemWindow::wakeEventType()`) or posts GLFW's empty event. `post(task)` (from any thread, the other call allowed off the UI thread; the UI stays single-threaded) queues a `std::function<void()>` under a mutex and calls `requestFrame()`; `runPosted()`, first in `drawAll`, runs the queue in posting order outside the lock (a task posted meanwhile waits for the next frame; when one throws, the rest of its batch goes back to the front of the queue and the exception propagates). `needsFrame()` reads the queue's own flag, since the layout clears the request after `runPosted` and a post in between would otherwise go unseen. A hidden window (`windowVisible()` false, after `setWindowVisible(false)` or `close()`; not when minimized) doesn't draw, so it doesn't run its posts until it draws again: producers posting to one should stop or coalesce. A task must not capture a `shared_ptr` to the window (the queue would keep it alive: a cycle), but a `weak_ptr` or a raw pointer whose lifetime the caller guarantees. Tasks still queued when the window is destroyed are destroyed without running: stop posting before destroying the window. `SDL3Application::run` draws a window after any event for it and while `untilNextFrame` is zero, and otherwise sleeps in `SDL_WaitEvent`, or `SDL_WaitEventTimeout` until the soonest timer of the visible windows (rounded up to a millisecond); live resizes still draw from the event watch, and the system theme change marks every window. GLFW owns no loop: `example/glfw-host` shows a host waiting with `glfwWaitEvents`/`glfwWaitEventsTimeout` from `untilNextFrame`. Toasts don't count the time since the last update when the mouse is over the stack now or was then, since frames stop while nothing changes and the mouse leaving brings the next one. There is no caret blink (nothing else needs frames).
- **Animation** (`psychic-ui/animation/`): a `Timing` is a duration along an `Ease` (a cubic Bézier, CSS's: `Ease::Linear`, `Standard` (CSS's `ease`), `In`, `Out`, `InOut`, or `Ease{x1, y1, x2, y2}`), a `Spring` (`stiffness`, `damping`, `mass`; `Spring::Gentle` critically damped, `Snappy`, `Bouncy`), or instant (the default, or 0 ms). `Timing::approach(offset0, velocity0, seconds, tolerance)` (`Timing.cpp`) answers where a value is as an `Approach` (its offset from the target, which goes to 0, its velocity, whether it settled), handing it to the kind's own math: `Ease::approach` (the offset along the curve, its velocity from the Bézier's derivative, `Ease::slope`; settled when the duration is over) or `Spring::approach` (solved in closed form, so the frame rate doesn't change it; settled within the tolerance, or after `Spring::maxTime`). A `Tween` (`Tween.hpp`) moves up to four channels (`Channels`) at explicit times, asking its timing where each channel is and knowing nothing of the kinds: a retarget starts from the current value, with its velocity when `Timing::keepsVelocity()` (a spring; a curve starts from rest and takes its whole duration again); a spring settles within a thousandth of its way. `Interpolation<T>` (`Interpolation.hpp`) turns a value into channels and back (float, `Color` premultiplied, `Length`, whose unit comes from the target) and says where a move from one value toward another ends (`target(from, to)`: nothing when they don't interpolate, a `Length` that is auto or changes unit, zero being zero in any unit), for `Animated<T>` and the style transitions. `Animated<T>` (`Animation.hpp`) is a member of a div (`Animated<float> _x{this, 0.0f, Timing{...}}`; `to(target)`, `jump`, `value()`, `animating()`, `timing(t)` for the next move) and `Div::animate(from, to, timing, callback)` is fire and forget, held by the div. Both are `Animation`s the window ticks in `updateAnimations` through weak pointers (`startAnimation`), so they end with their owner. A tween started after `updateAnimations` and before `drawAll` ends starts at that time (`animationClock()`); one started between frames (from an event) starts with the next frame. Everything jumps when the owner isn't in a window, the timing is instant, or `Window::reducedMotion()` (off by default: SDL doesn't expose the system's preference; turning it on ends what moves). `Window::animationSpeed(s)` (1 by default) runs the animation clock at `s` times the real one, for slow motion; timers keep the real time. **Entering and leaving**, CSS's `@starting-style` and Base UI's starting and ending styles, for any div: `startingClass("entering")` gives it that class for its first style in a window only (its descendants' first styles see it too); nothing of it transitions while it has it (`starting()`), and the window lets it go in the frame's `updateStylesAndLayout`, after the layout and the popups' placement and before the first paint, so its transitions start from what that class's rules say. `exit(className, done)` gives it the class, takes the mouse from it and styles it at once: when nothing of it transitions it calls `done` (which removes it) right away, else the window does once neither it nor a descendant transitions (`subtreeTransitioning()`), after a style pass; `exiting()`, `cancelExit()` (it stays, its transitions head back). Both are instant with reduced motion, and `exit` on a div never painted (still `starting()`) or not in a window; leaving the window drops both. **Layout transitions** (FLIP): a container's `layoutTransition` style property (a `Timing`, instant by default, not inherited; a property rather than a method so that a skin set's rules turn it on) makes its children slide when a layout moves them. After every layout, `Window::slideLayout` walks the tree (`Div::updateLayoutSlides`, skipping `display: none` subtrees): each child of such a container compares where the layout puts it in the window, scrolling aside (so scrolling never slides anything), with where it was painted, and its paint offset (`layoutOffsetX()`/`layoutOffsetY()`, `layoutSliding()`, added to its `translateX`/`translateY` when painting) starts from the difference and tweens to 0; one already sliding retargets from where it is painted, and the ancestors' offsets that start in the same walk are taken out, so a child carried by a sliding container doesn't slide twice. Yoga runs once, hit testing finds the layout place. Nothing slides on a child's first layout in its container (an added child appears in place, and so does one shown again after `display: none`; one removed and added back before the next layout, `RowGroup::reorder`, slides), on a window resize, with new rules (`rulesGeneration`: a theme, a density, a skin set), or with reduced motion. Sizes don't animate. A child has the `sliding` class while it slides (`updateSlidingClass`, set in the walk and styled again before the paint, removed when its tween ends; its rules should only paint), and a div paints its children that don't slide first, then those that do, each in document order, so what moves passes over what stays (rows sorted, or a tree's nodes over the children fading in). Each child sliding holds one two-channel tween, made the first time it is laid out in such a container; the window idles once they settle. The fling is physics following the finger and stays.
- **Touch and pens**: `Window::inputMode()` is `InputMode::Pointer`, `Touch` or `Pen`, set by the backends through `handleInputModeChange` (`onInputModeChange`/`inputModeChanged`); in touch mode `:touch` matches every div of the window (`Window:touch Button`). The SDL3 adapter follows the first finger on a touch screen (`SDL_TOUCH_DEVICE_DIRECT`; trackpads, other fingers and the mouse events SDL makes of touches and pens are ignored, so a tap arrives once; `touchDeviceType` is virtual for the tests) and calls `Window::handleTouchPress`/`Move`/`Release`/`Cancel` with SDL's timestamps; real mouse motion or buttons switch back to pointer. The window turns touches into mouse events: a tap clicks where the finger landed; past `touchSlop` (8 px) it pans the deepest `overflow: scroll` div under the finger that can scroll along the drag's main axis, else it presses there and drags; held `longPressDelay` (500 ms) it is a right button press, released when the finger lifts, which never clicks (and asks for a context menu). Its mouse events say `source` `Touch`. A pan that lifts while moving flings (kinetic scrolling, decaying by `flingDecay` per ms), advanced by `updateGestures(time)`, which `drawAll` calls each frame with the system window's `gestureTime()` and tests call with their own times; a finger stops it. A pen is a mouse in pen mode (tip left, barrel buttons right and middle). GLFW has no touch input: its adapter never changes the mode. A focused text field that can be typed into (enabled, not read-only) tells the system window its caret's line in every input mode, whenever the caret moves or the field is laid out after an edit (`TextField::revealCaret`, `Window::setTextInputArea`, `SDL_SetTextInputArea` in SDL3), so the on-screen keyboard avoids it and an input method places its candidates by it.
- **Light and dark**: a window follows the system's color scheme until a theme is picked (`followsSystemTheme()`): the skin set's `lightTheme()` while the system is light, its `darkTheme()` while it is dark, its `defaultTheme()` while it doesn't say (`SkinSet::theme(scheme)`; light and dark default to the default theme, Pivotal Dark for the default set, Float Light for Float), switched live; `Window::theme(t)` stops following, `followSystemTheme()` resumes it, optionally with a pair of themes. **Switching skin sets** (`Window::skinSet`) keeps whether the window follows the system: a theme picked with `theme(t)` stays picked, itself if it is one of the new set's `themes()` (by name, `SkinSet::hasTheme`), else the new set's theme of the same scheme (its `lightTheme()` for a light theme, its `darkTheme()` for a dark one); a window following the system keeps following it, with the pair given to `followSystemTheme` if both are the new set's, else with the new set's own light, dark or default theme. A set's `themes()` are those made for it, as a picker lists them (its light, dark and default ones unless it says more; the default set adds One Dark, One Light and Psychic). The system window reports the scheme when it attaches and on changes (`Window::handleColorSchemeChange`, then `colorSchemeChanged`/`onColorSchemeChange`): the SDL3 adapter from `SDL_GetSystemTheme` (`colorScheme()` is virtual for the tests) and `SDL_EVENT_SYSTEM_THEME_CHANGED`, which names no window, so `handleEvent` takes it whatever window and `SDL3Application` sends it to every window.
- **Overlay and popups** (`Overlay.hpp`, `Popup.hpp`): the window's last child, above `appContainer()`, is its `Overlay` (`Window::overlay()`), filling it; its children are `Popup`s, the last on top: menus, select lists, tooltips, dialogs, the toasts' stack. `overlay.open<T>(args...)` (or `open(shared_ptr)`) adds one on top and calls its `opened()` (where it takes the focus), and its `laidOut()` after the next layout (when what was added after `open` is there), `popup.close()` closes it (the popups it owns first, `owner(popup)`: a submenu) and emits `closed`. **Entering and leaving**: a popup has the `entering` starting class (`Div::startingClass`), and once placed its side as a class (`side-bottom`, `side-top`, `side-right`, `side-left`) and its transform origin at its anchor (the anchor's middle on its facing edge, Base UI's `--transform-origin`), so a menu scales from its trigger and a context menu from the pointer. `close()` is an `exit("exiting")`: the popup is closed at once for everything (`isOpen()` false, `modal()` false, no mouse, out of `focusScope`, `popups()`, `top<T>()`, `pressOutside`, `dismissTop`, `closeAll`; the focus goes back now; `closed` is emitted now, so `Window::menuClosed`, a select's `open` class and `isOpen()` follow at once) but stays in the overlay, where it was placed, until its and its descendants' transitions end, then is removed (its `removed()`); without exit rules, never painted, or with reduced motion it is removed at once. Opening it again while it leaves (`overlay.open(popup)`) cancels the exit and raises it without re-adding it: its transitions head back from where they are; a menu does this for the submenu of the row it is hovered back onto, the window for the tooltip of the same div. A popup is placed beside an anchor, a div (`anchor(div)`, held weakly: it closes when the div leaves the window) or a point in window coordinates (`anchor(x, y)`), on a `side` (`Side::Bottom`, `Top`, `Right`, `Left`) with an `alignment` (`PopupAlign::Start`, `Center`, `End`), `sideOffset` and `alignOffset`, by `placePopup` (a pure function: it flips to the opposite side when it doesn't fit and that side fits or has more room, then shifts along the side to stay inside the window less `collisionPadding`, 12); `updateStylesAndLayout` places the anchored popups after the layout (`Overlay::place`) and lays out again when one moved, every frame, so a popup follows its anchor; `placedSide()` and `anchorRect()` say where it went (a tooltip's arrow). Unanchored, a popup sits where its style puts it (a dialog fills the overlay, the toasts' stack is in a corner). Mouse input: the overlay only takes it where a popup does (`Overlay::dispatch`, topmost first; a popup with neither `mouseEnabled` nor `mouseChildren` lets it through, a tooltip), and everywhere under a `modal` popup, which keeps it from the content and the popups under it except its `passThrough(div)` divs (a menu bar, so that hovering another trigger switches menus); the window's hit path (`hitPath`, used by hit slop, touch panning and tooltips) follows the same rule, and `isDragArea` is false under a modal popup or on a popup. Dismissal: before a press is dispatched, `Window::handleMouseButtonChange` calls `Overlay::pressOutside`, which closes, topmost first, the popups the press is outside of (outside their `surface()`, a dialog's panel) that `dismissOnOutsidePress` (the default), stopping at one it is inside of, a pass-through div, or a modal popup that stays; when that closed a modal popup, the press and its release go no further, except a right press that only closed popups that `passesContextPress` (menus): it goes on, so that a right press elsewhere while a context menu is open opens the context menu there (or the new target's), as macOS and Windows do. Escape closes the topmost popup that `dismissOnEscape` before the focus path sees the key (`Overlay::dismissTop`), unless a div on the focus path has a use for it (`Div::takesEscape()`: a `SearchField` with text clears it, a `NumberStepper` whose typed text isn't its value reverts), as browsers do: then the key goes to the focus path, and the next Escape closes the popup. Focus: `trapFocus` keeps Tab within the topmost popup that traps it (`Overlay::focusScope`); a popup notes what had the focus when it opened and, closing with the focus inside it, gives it back with the same `focusVisible` (`restoreFocus`, the default). `Window::updatePopups(now)` advances what goes with time (tooltip delays, toast timers), from `drawAll` with the system window's `gestureTime()` like `updateGestures`, and from tests with explicit times.
- **Menus** (`components/Menu.hpp`): items are data (`MenuItem`: label, shortcut, icon, `enabled`, `danger`), made into rows each time a menu opens, so they keep their state: `Menu::item(label, callback, shortcut, icon)`, `Menu::item(label, items)` (a submenu), `Menu::check(label, checked, callback)` (toggled when chosen, the menu stays open), `Menu::radio(group, label, value)` (a `MenuRadioGroup` holds the value and its callback; `closes` makes choosing one close the menu, as a select's list does), `Menu::separator()`, `Menu::group(label)` (a group label). A `Menu` is a modal popup of `MenuButton` rows (`rows()`), `.separator` divs and `.group-label` labels; when one row has an icon every row keeps the icon column, and when one is checkable every row keeps the check column (`MenuButton::setColumns`; the `.check` part before the icon, or the `.indicator` part after the label with `checksAfter(true)`); a checked row has the `checked` class, a danger one `danger`. One row is highlighted (`highlight(index)`, its `selected` state, `:active` in rules) by hovering it or by the keyboard (the menu has the focus): Up and Down (wrapping, over disabled rows), Home, End, Right or Enter on a submenu row opens the submenu and moves into it, Left in a submenu closes it, Enter or Space chooses (`choose(index)`), Escape closes the topmost menu; Left or Right past a menu bar's menu opens its neighbor (`navigatedOut`). Submenus open beside their row (`Side::Right`, first rows level), flip left at the window's edge, and are not modal so that the mouse still reaches their menu; hovering opens them without moving the focus. `Window::openMenu(items, x, y)` (at a point), `openMenu(items, anchor, side, align)` (beside a div, 6 px away) and `openMenu(shared_ptr<Menu>)` close the open menu first, emit `menuOpened`, and `menuClosed` when it closes; `closeMenu()` closes it. `Div::contextMenu(items)` gives a div a context menu: it subscribes to its `contextMenuRequested` (so the deepest div with one on the hit or focus path opens its own) and calls `Window::openContextMenu(items, x, y, fromKeyboard)`, which opens it at the point with the `context` class; from the keyboard (`MouseEvent::fromKeyboard`, set by `mouseEventAtCenter`: the Menu key, Shift+F10) the menu takes the focus visibly at its first enabled row. A touch long press is the context press first; only when it opened nothing does the tooltip show. `MenuBar` opens its menus under their triggers, as pass-through.
- **Select** (`components/Select.hpp`): a focusable closed field (`.value`, with the `placeholder` class while nothing is chosen, then `.chevron`) whose options (`options`, `selectedIndex`, `value()`, `placeholder`) open in a `Menu` with the `listbox` class below it, at least its width, the chosen option highlighted and checked after its label; a click, or Enter, Space, Up or Down, opens it; choosing emits `changed` (`onChange`) with the index; the field has the `open` class meanwhile. A press on the field while it is open closes the list (outside press) without reopening it.
- **Tooltips** (`components/Tooltip.hpp`): `div.tooltip("text")` (a `Div` property, not a style) is shown by the window in a `Tooltip` popup (above, flipped below, an arrow at the anchor, no mouse input, the focus untouched) once the mouse has rested `tooltipDelay` (300 ms) on the deepest div with one (`Window::handleMouseMove` follows it, not while a button is down; the delay counts from the next `updatePopups`), at once when another hid less than `tooltipWarmTime` (400 ms) before; a press or a key hides it until the mouse reaches another. By touch, hovering doesn't exist and a long press is the context press (a right button press): the rule is that the context press comes first, and when it opened nothing (no new popup on top of the overlay) the tooltip of what is under the finger shows until the finger lifts; so a div with a context menu never shows its tooltip by touch.
- **Dialogs** (`components/Dialog.hpp`): a modal popup filling the overlay (the `scrim` color) with its `.panel` in the middle (its surface): `.header` (`.icon`, `.title`, a `.close` icon button), `.body` (`.description`, then what is added to `body()`), `.footer` (shown once an `action(label, callback, variant, closes)` is added, after a hairline); `wide(true)` for the 560 px width; a press on the backdrop closes it unless `dismissible(false)`, Escape always; it focuses its panel when it opens, then, once laid out with what was added to it (`Popup::laidOut`, called once from `Overlay::place` after the first layout since it opened), its first field (a focusable div of the body that isn't a `Button`), else its first button (the body's, then the footer's), else the panel keeps it, as Pivotal and Base UI do; `initialFocus(div)` picks another; a button gets its ring when the focus was visible as it opened. It traps Tab and gives the focus back.
- **Toasts** (`components/Toast.hpp`): `Window::toast(ToastOptions)` adds a `Toast` (title, description, `ToastVariant` `Info`, `Success`, `Warning` or `Danger` as a class and the icon's tile, actions, a close button) to the window's `ToastStack` (`Window::toasts()`, a non-modal popup in the bottom right corner that Escape and outside presses leave alone), the newest at the bottom, at most `ToastStack::limit` (3, the oldest goes). Each closes after its `timeout` (5 s; 0 keeps it), counted by `updatePopups` and held while the mouse is over the stack, or when an action (unless `keepOpen`) or the close button is clicked (`dismissed`, emitted as it starts leaving). A toast enters with the `entering` starting class and leaves with `exiting` (`Div::exit`), out of `toasts()` and the limit meanwhile; one pushed out by the limit also has `limited`. A dismissed toast leaves the stack's flow at once, where it is (absolute, from the stack's bottom edge, which stays in the corner), so the others slide into its place as it goes (the stack's `layoutTransition`); one with a toast still under it (from the middle, or `limited`) also has `in-place`, and fades where it is rather than sliding down over that one.
- **Window dragging**: `Window::addDragArea(div)` (`TitleBar` and the `AppShell` sidebar's header register themselves) and `Window::isDragArea(x, y)`, which SDL's hit test asks before a press is delivered, so the window manager or compositor moves the window (on Wayland too). `startDrag()`/`stopDrag()` remain as the fallback where there's no hit testing; `Window::supportsDrag()` is false where neither works (GLFW on Wayland).
- **Style system** (`psychic-ui/style/`): `StyleManager` holds selector→`StyleDeclaration` rules (descendant selectors on tags and `.class`es, matched case-insensitively), fonts, the theme and the skin set. The cascade follows CSS: matching rules apply by weight (specificity), and on equal weight the rule declared last wins (rules are kept in declaration order). Rules are indexed by what their rightmost part requires (id, else first class, else tag), so a Div is only tested against the rules indexed under its own id, classes and tags, plus the pseudo-class-only ones. An unparsable selector throws `std::invalid_argument`. `reset()` empties the rules but keeps them allocated, so a `Style &` from `style()` never dangles; a rule declared again starts empty, after the others. A `StyleSheet` subclass implements `load(StyleManager*)`, writing its rules from `manager->theme()`. Windows apply them with `loadStyleSheet<T>(reset)`, and loading several stacks them over the skin set's rules (e.g. `DemoStyleSheet`); the style manager keeps them, in load order (a type loaded again runs again in its place). Each `Div` gets a computed `Style` (`computeStyle`: the `*` rule, then what it inherits from its parent, the matching rules, its inline style, and its `_defaultStyle` for what's still unset). `styleUpdated()` is the hook for reacting to it; it must assign derived state from the computed value or its default every time, so that a rule that stops matching (`:hover`, a removed class) takes its effect away. Some properties are inherited down the tree (`inheritedProperties()`, a mask; skins inherit almost everything from their component).
- **Style properties are defined once**, in the `PSYCHIC_UI_STYLE_PROPERTIES` X-macro of `style/Properties.hpp`: name, stored type, setter argument type, default, inherited or not, layout (read by Yoga) or paint-only, animatable (colors, numbers and lengths but `hitSlop`; `animatableProperties`). It generates the `Property` enum, the flat `StyleValues` struct, the inherited/layout/paint masks, and `Style`'s typed getter and chainable setter for each (`manager->style("Button").padding(12).cursor(Cursor::Hand)`, `computedStyle().fontSize()`). A `Style` is that struct plus a `std::bitset` of which properties are set: copying, overlaying and comparing never allocate, and `diff` gives the changed mask, from which `Div::updateLayout` pushes only the changed layout properties to Yoga (paint-only changes never touch it). To add a property: add its line to the table; if it is a layout property, push it in `Div::updateLayout` (Div.cpp); otherwise read it where it is drawn. `hitSlop` (window units, not inherited, paint-only) widens where presses reach a div without changing its look: a press that lands on nothing taking presses (no button, press, release, click or context menu subscriber on its hit path) goes to the div with a slop reaching it whose center is nearest, moved onto its edge (`Window::handleMouseButtonChange`, `hitSlopTarget`); it applies in every mode, and the skin sets give it a value only in touch density. **Transitions**: the `transition` property (a `Transition`: up to four timings, each for a set of properties; `style.transition(Property::backgroundColor, Timing{100ms})` or `transition({...}, timing)` add to it, in rules and inline, and `transition(Transition{})` turns them off) cascades as a whole like CSS's and isn't inherited. When a div's computed style changes an animatable property its new style's transition names, `Div::updateTransitions` (`animation/StyleTransitions.cpp`) starts a tween from the painted value toward the end `Interpolation<T>::target` gives, kept in the transitions' `targets` style (a color that appears fades in from transparent, one that goes fades out and ends unset; a length that changes unit or goes auto snaps), retargets a running one from where it is, or drops it when the new style has no transition for it; the window ticks it (`Div::advanceTransitions`, which writes the value, pushes layout properties to Yoga, runs `styleUpdated` and restyles the children that inherit it). So `computedStyle()` is the blend, what is painted and laid out, updated every frame while it moves; `targetStyle()` is where it goes, `transitioning(property)` says whether it moves. Children inherit the blend. Nothing transitions on a div's first style in a window (`_styledIn`), when the rules reloaded (`StyleManager::rulesGeneration()`: a theme, a density or a skin set switch changes at once), or with reduced motion. A transitioning layout property lays the tree out every frame (Yoga reuses the clean subtrees): the default set keeps that to the switch's thumb (`grow`) and a slider stepped by keys; `grow` and `shrink` reach Yoga clamped at 0, as springs overshoot. `gap` (and `rowGap`/`columnGap`) is Yoga's gap between children; `HBox`/`VBox` (`components/Box.hpp`) are just presets for `direction` and `gap` in the default style.
- **Style values** (`style/Values.hpp`, which includes the headers of the three classes) are typed, so mistakes don't compile: `Length` (`style/Length.hpp`; a number is pixels, `50_pct` is percent 0-100 like CSS, `Auto`; the literals are in the inline namespace `psychic_ui::literals`), scoped enums for every enumerated property (`Direction` is the flex axis, `TextDirection` is ltr/rtl, `Justify`, `Align`, `Position`, `Wrap`, `Overflow`, `Display`, `BoxSizing`, `TextAlign`, `Cursor`, `Orientation`), `Color` (`style/Color.hpp`; only from `rgb(0xRRGGBB)`, `argb(0xAARRGGBB)`, `Color::fromARGB` or a psychic-color color; `.argb()` gives Skia's `SkColor`, `a.over(b)` composites a over b), and `Atom` (`style/Atom.hpp`, interned strings) for the open sets, font family and skin name. The setters' argument wrappers (`detail::BoolArg`, `FloatArg`, `StringArg`) reject `"false"` for a bool, `0` for a string and a bool for a number. `themes/palette.hpp` has named colors in `psychic_ui::palette`.
- **Themes** (`psychic-ui/themes/`): a `Theme` (`Theme.hpp`) is values only: its `name`, its `scheme` (`ColorScheme::Light` or `Dark`), and four groups, on Pivotal's token roles (`packages/ui/src/styles/tokens.css`): `Palette` (layers `base`, `surface`, `raised`, `overlay`, `frame` (the app frame), `page` (the inset page panel), `hover`; hairlines `line`, `lineStrong`; text `text`, `textSecondary`, `textMuted`; `accent`, `accentHover`, `accentText`, `accentSoft`, `onAccent`; `danger`, `dangerText`, `warning`, `warningText`, `success`; `scrollThumb`, `scrollThumbHover`, `scrim`, `switchOff`; `canvasDot`, a canvas's dots over the `frame` color), `Elevation` (`Shadow`s: the two-layer `overlay` + `overlayContact`, `thumb`, and `panel` + `panelContact` for panels floating over a canvas, which every named theme sets: lower than `overlay`, a soft drop over a 1 px ring (in the default set's themes, whose canvas is their panels' color, the strong hairline in light and a step past it in dark, where the shadow swallows it)), `Typography` (the three fonts, and Pivotal's scale as `TextStep`s of size and leading: `xxs` 10/14, `xs` 11/16, `sm` 12/18 (body), `base` 13/20 (inputs, menu rows), `md` 14/20, `xl` 18/26, `xxl` 20/28) and `Metrics` (`Radii` by role: control 8, button 999 (pills), surface 12, popup 16, row 8, page 16, check 4, small 6; border, focus ring 2 offset 1, the 4 px spacing scale `space(n)` named like Pivotal's `--space-n`, gutters, the frame inset 8, bars 44 and 52, the sidebar's and a menu's widths, thin scroll bars, icon sizes and stroke; and the `Sizes` that follow the density: `pointer` and `touch` values for `controlXs`/`Sm`/`Md` (20, 24, 28), `rowSm`/`Md` (32, 40), `textStep`, `iconStep` (added to `iconSm` and `iconMd` wherever the default set sizes icons) and `hitSlop`; and `Motion`, Pivotal's: `fast` 100 ms, `medium` 150 ms, `slow` 240 ms (not Pivotal's, for what travels further: the default set's data grid rows as they're sorted), the `standard` curve (CSS's `ease`, which Pivotal's color transitions use), `out` (`--ease-out-quick`, cubic-bezier(0.16, 1, 0.3, 1)) and a `spring` (500, 40) for what is thrown or dragged, with `quick()`, `moderate()`, `arrive()`, `enter()` (`medium` on `out`, a popup appearing) and `leave()` (`fast` on `out`) timings; Float's are a little slower, its spring softer). The named ones are `constexpr`: `themes::pivotalDark` and `themes::pivotalLight` (`pivotal.hpp`, Pivotal's tokens value for value with its `color-mix`es precomputed; the default skin set's), `themes::oneDark`, `themes::oneLight` and `themes::psychic` (their colors on the same roles, in Ubuntu), `themes::floatLight` and `themes::floatDark` (`float.hpp`, Float's, with its `floatTypography` and `floatMetrics`), `themes::deskDark` and `themes::deskLight` (`desk.hpp`, Desk's: Pivotal's palettes, elevations and motion, Desk Light on a white base and page, with its `deskType` and `deskMetrics`); groups mix with designated initializers. `StyleManager::theme(t)` (or `Window::theme(t)`) stores it, clears the rules (fonts and skins stay) and loads every kept stylesheet again in order, so app sheets that read the theme follow it and their rules still win; rules declared outside a stylesheet are dropped (`Window::theme` recreates the runtime ones, `createStyles`). The style manager's `density()` (`Density::Pointer` or `Touch`) picks the sizes stylesheets read with `manager->sizes()`; switching it replays the stylesheets the same way, which a window does when it enters or leaves touch mode (a new window starts at the pointer density; the manager is shared, so the last window to switch decides). The default skin set's sizes are the same in both densities except the hit slop (0 with a pointer, 10 by touch, so a 24 px control reaches 44 px), so nothing looks different by touch; Desk's differ (see **Desk**). A new style manager starts with Pivotal Dark.
- **Component/Skin split**: `Component<SkinT>` (`Component.hpp`) is a `Div` whose visuals come from a skin child implementing `SkinT`, the component's skin interface (`ButtonSkin` in `components/Button.hpp`, `RangeSkin` in `Range.hpp`...). The skin is always child 0 and draws the component; the component's own `draw` is a no-op and it ignores internal layout constraints: its padding, border and content layout (`direction`, `justify`, `align*`, `wrap`, `gap`) aren't pushed to its own Yoga node but inherited by its skin, which grows to fill it. Skins come from the style manager's **skin set** (`skins/SkinSet.hpp`, decisions D2, D3, D5, D9): a `SkinSet` is a `StyleSheet` that also registers a skin per interface and variant in a typed `SkinRegistry` (`skins.add<ButtonSkin, ButtonSkinBase>()`, `.add<ButtonSkin, TabButtonSkin>("tab")`; a variant's skins have its name as a class, so one skin serves several variants: `.add<ButtonSkin, ButtonSkinBase>("primary")`, which rules reach as `Button ButtonSkinBase.primary`), names its `defaultTheme()` and may name a `fallback()` set for what it lacks (its skins and rules go first, under the set's). `window.skinSet<PivotalSkins>()` (or `StyleManager::skinSet<S>()`, or `loadStyleSheet<S>()`) installs one per style manager (the window picks the theme as **Light and dark** says, the style manager alone the set's theme for a scheme or a given one, `StyleManager::skinSet(set, theme)`; `window.skinSet(std::unique_ptr<SkinSet>)` takes a set made elsewhere) and bumps `skinsGeneration()`; `Component::styleUpdated` hatches `styleManager()->skin<SkinT>(variant)` when the `skin` style property (the variant name, "" for the default) or the generation changes: the variant from the set or its fallbacks, else the interface's default, so never no skin once a set is in use. `.skin(std::make_shared<MySkin>())` sets one by hand, kept until the property or the set changes. On a re-hatch the old skin is removed with its parts and the new one added as child 0, then the component's `skinChanged()` runs: a component never lends a part of its own to its skin, so a text field's (`TextInput`, `TextArea`, `SearchField`, `NumberStepper`) skin creates its own view and the field pushes its whole state to it (`TextField::skinChanged`). Skins paint with `paint/` (stateless primitives, which `Icon` uses too: `paint::Box::of(div)` is a div's border box as an `SkRRect` from its computed radius and border, `fill`, `stroke`, `arrow`, `disc`, `circle`, `icon`). A skin has two layers. The interface, beside its component, is the data going in (`setLabel`, `setIcon`, `setText`, `setValue`..., virtuals that do nothing by default, so a skin may ignore them) and the answers the component needs back (`valueAt`, `trackRect`/`thumbRect`, `positionAt`, `segmentAt`, `swatchAt`, `clearAt`, `partAt`, and `textView()`, the text fields' view part), pure virtual: implementing it directly makes a truly custom skin (`TitleBarButtonSkin`, a disc without parts). `skins/base/` holds one concrete base per interface (tagged with its class name, `ButtonSkinBase`, so rules can target it), which a set registers as it is and which creates the **parts contract**, the class names app rules can target with any set: `Button .icon` (`Button::icon(name)`, not displayed without one), `.label` (not displayed when empty); `CheckBox .box`, `.label` (and the check box's `checked` class); `ScrollBar .track`, `.thumb`; `Range .track` with `.fill` (from the start, or the bottom, to the value) and `.thumb` (centered on the value, in a zero-size `.thumb-anchor` placed at it) inside it, then `.value`, and the skin's `.horizontal`/`.vertical`, the base placing the fill and the thumb and answering `valueAt` along the track; `MenuButton .check` (displayed in menus with checkable rows), `.icon` (`MenuItem::icon`, displayed in menus with icons), `.label`, `.shortcut`, `.indicator` (the check after the label, in a select's list), `.arrow` (a chevron, displayed for a submenu), and the row's `checked` and `danger` classes; and calls one `drawChrome(canvas, box, SkinState)` hook from `draw`, the override point for a skin that only changes the chrome; the check box's draws the check mark). Skins only draw and say where things are (decision D4): components own the input, so a new look never reimplements it. `Range` handles presses and drags and asks its skin `valueAt(x, y)` (the linear value at a point), `ScrollBar` drags the thumb from its skin's `trackRect()` and `thumbRect()`, and one directory per set: `pivotal/` is `PivotalSkins` (named "Default": the library's own set), its rules and the skins that draw Pivotal's way (`TabButtonSkin`, `TitleBarButtonSkin`, `PivotalAvatarSkin`); `desk/` is `DeskSkins`, P2 Desk; `float/` is `FloatSkins`, the sample set.

its own `changed` is the value's, a `double`, emitted when the value changes, not as its text is edited): its skin's `.decrement` and `.increment` buttons (Divs with the `minus` and `plus` icons, `:disabled` at the bounds through `NumberStepperSkin::setBounds`, their hover and pressed looks from rules) around the `.value` view; a press on a button (the skin's `partAt(x, y)`, through `fieldPress`), Up/Down (Shift ×10) and the wheel while focused step it, typed text is set on Enter or blur, Escape reverts (`fieldKey`); what is typed or stepped is rounded to the decimals shown, and a step they can't show moves by one of their units; no press-and-hold repeat (no timer). `ColorSwatches` (`colors`, `selected()`, `value()` a `Color`; Pivotal's palette by default, `palette::pivotalSwatches`): `.swatch` chips wrapping into a grid, the selected one ringed in the accent; a press selects at once; one Tab stop with a focus of its own among the chips, apart from the selection (`focusedSwatch()`, the `.focused` part): it starts on the selected chip, else the first, each time the group takes the focus, the arrows, Home and End move it without selecting, Space or Enter selects its chip; while the focus is visible it is ringed in a neutral grey (`textMuted`), in the accent when it is the selected one; the skin answers `swatchAt` (the nearest chip).
- **Signals** (`psychic-ui/signals/`): header-only `Signal` (`subscribe`, `emit`), `Slot`, `ScopedSlot` (owns a subscription: disconnects when destroyed or assigned another) and `Observer` (`subscribeTo`, ended with the observer). `Div` is an `Observer`, so its subscriptions are torn down with it.
- **Events** follow one convention: a chainable connector `on` + a verb in the present tense, and the `Signal` member it subscribes to, named with the same verb in the past tense: `onClick`/`clicked`, `onDoubleClick`/`doubleClicked`, `onMousePress`/`mousePressed`, `onMouseRelease`/`mouseReleased`, `onMouseReleaseOutside`/`mouseReleasedOutside`, `onMouseButtonChange`/`mouseButtonChanged` (press or release), `onMouseMove`/`mouseMoved`, `onMouseEnter`/`mouseEntered`, `onMouseExit`/`mouseExited`, `onMouseScroll`/`mouseScrolled`, `onContextMenuRequest`/`contextMenuRequested`, `onKeyPress`/`keyPressed`, `onKeyRepeat`/`keyRepeated`, `onKeyRelease`/`keyReleased`, `onType`/`typed`, `onFocus`/`focused`, `onBlur`/`blurred`, `onScroll`/`scrolled`, `onResize`/`resized`; components add `onChange`/`changed`, `Window` `onMenuOpen`/`menuOpened`, `onMenuClose`/`menuClosed` and `onInputModeChange`/`inputModeChanged`. A new event follows the same rule. Connectors are declared with `PSYCHIC_UI_EVENT(connector, signal)`, which subscribes for the Div's lifetime and returns `Self &`. Use the signal itself (`button.clicked.subscribe(...)`, kept in a `ScopedSlot`) to stop listening early, and `subscribeTo` to listen to something that may die first. Callbacks capture `this` or raw pointers, never a `shared_ptr` to the Div that owns the signal (a cycle that leaks). Whether a div has the focus is `hasFocus()`. A `Signal` also takes a callback with no parameters, which ignores its arguments (`onClick([] { ... })`). Every mouse signal passes one `const MouseEvent &` (`psychic-ui.hpp`, a plain aggregate): `x`/`y` in the receiving div's content coordinates (from its top-left corner, plus its scroll offset, as before), `windowX`/`windowY`, the `button` that changed (`NONE` for moves and scrolls), `down` (for `mouseButtonChanged`), the `buttons` held after the change, `modifiers`, `clickCount` (1, 2, 3... for presses in a row of one button, kept for their release and click; 0 when no press made it: moves, scrolls, and clicks or context menus from the keyboard), `source` (`InputMode`: `Touch` for the window's touch gestures, `Pen`), `fromKeyboard` (made by a key in place of the mouse, by `mouseEventAtCenter`) and `scrollX`/`scrollY`. `mouseEntered`/`mouseExited` pass the move that entered or left, so a hover from a finger can be told apart. The backends fill it in window coordinates; the window adds `windowX`/`windowY`, `buttons` and, when the backend leaves it 0, `clickCount` (SDL gives its own, from the system's settings; GLFW's and pens' presses are counted within `multiClickDelay`, 500 ms, and `multiClickDistance`, 4 px; taps on the touch clock within twice `touchSlop`). `contextMenuRequested` asks for a context menu: on a right button press, after `mousePressed`, as on macOS and Linux, or on its release, after `mouseReleased`, as on Windows (`Window::contextMenuOnRelease()`, true under `_WIN32`, settable for tests), so also a pen's barrel button and, where `Window::ctrlClickIsRightClick()` (true under `__APPLE__`, as Cocoa apps do: AppKit delivers a left press with Control, and SDL doesn't convert it by default), a left press with Control and no other modifier, which the window turns into the right button for the press and its release (no click; GLFW gets it too); a touch long press always on the press (it is held), and from the Menu key or Shift+F10 on the focused div, at its center, before the keys reach `keyPressed`; the deepest div with a subscriber on the hit or focus path gets it, once. `Button` and `SidebarItem` clicked by Enter or Space emit `clicked` at their center (`Div::mouseEventAtCenter()`). The virtual dispatch methods the window and backends call use the same verb, `handle` + the connector's verb, and take the event in the parent's coordinates: `handleClick`, `handleMousePress`, `handleMouseButtonChange`, `handleMouseMove`, `handleContextMenuRequest`, `handleKeyPress`, `handleType`, ... A press that starts on a Div ends there: `mouseReleased` fires once per release, after `mouseReleasedOutside` when released outside. `clicked` and `doubleClicked` are left button only (so a touch tap clicks and a long press doesn't); the press, release and button change signals report every button. A div with a `clicked` subscriber swallows left presses, so a parent's `mousePressed` doesn't take them; `Button` looks pressed for the left button only.
- **Text**: `Text` is a measured Div showing its text with a `text/TextLayout`, laid out from its computed style (`styleUpdated` re-measures only when the layout style changes), and is the view text fields drive: `TextFieldBase` (`components/TextField.{hpp,cpp}`, a Div) holds the input glue once, and `TextField<SkinT>` makes it a component (`Component<SkinT, TextFieldBase>`: `Component`'s second parameter is the Div it extends, `Div` by default) whose skin's `textView()` is its view. It takes the focus itself (`:focus` and `:focus-visible` match the field), owns a `TextEditing`, takes its own `keyPressed`/`keyRepeated` (a protected virtual `fieldKey(key, mod)` first, the field held alive, then `handleKey` with the skin's view as geometry), `typed`, `focused`/`blurred` (`startTextInput`/`stopTextInput`) and presses (the left button: a protected virtual `fieldPress(event)` first, for a skin's button parts, then `selectAt` at the view's `indexAt` with the press's `clickCount`, then dragging on the window's `mouseMoved` until `mouseReleased`); after every edit it pushes the text, the selection and whether the caret shows (focused, enabled and not read-only) to its skin's `textView()`, reveals the caret (`Text::reveal`: one line scrolls horizontally, `offsetX()`, clipped to the view; several lines scroll the view's nearest scrolling ancestor, `Div::scrollIntoView(rect)`) at once or, when the text changed, in its `layoutUpdated`, tells the window where the caret's line is while it can be typed into, then calls `textChanged()` for subclasses and, when an edit changed the text, `textEdited()` (held alive), where each field emits its own `changed`: the text (a `std::string`) for `TextInput`, `TextArea` and `SearchField`, the value (a `double`) for `NumberStepper`, which emits it when what is typed is set, not on each edit; `TextField` declares no signal, so no subclass hides one. `text()`/`text(s)` (setting is no edit: no `changed`), `selection()`/`selection(anchor, caret)`, `caret()`, `readOnly(bool)` (edits refused; selection, caret moves and copy kept; no caret shown); disabled, it ignores input and doesn't take the focus. `TextInput` is a `TextField<TextInputSkin>`, whose skin creates its `.text` view (`textView()`) and `.placeholder` parts. `TextArea` is a `TextField<TextAreaSkin>` on several lines (Enter inserts a line return), whose skin creates its `.viewport` part (a `Scroller`) around its `.text` view, at least the viewport's height; `SearchField` and `NumberStepper` are `TextField`s too (see **Inputs**). The view paints the selection whenever there is one, unless `selectionBackgroundColor` is transparent, and the caret while `caretVisible`; rules decide how an unfocused selection looks (Pivotal hides it: transparent on `TextInput`, `TextArea`, `SearchField` and `NumberStepper`, the accent's soft color on `:focus`). `Text` takes no input: a text one can select and copy is a read-only field. `Label` is a `Text` on one line, tagged `Label` after `Text` (so `Text` rules match labels too); both keep the text as it was set (`text()` converts the UTF-16 back to UTF-8, by value). A text is as wide as its widest line within the width it is given and as tall as its lines times the computed line height, nothing more: glyphs overflow a line height smaller than the font's, as in CSS. One line too long for its box ends as the `textOverflow` style property says (not inherited): `TextOverflow::Clip` (the default) cuts it after the last character that fits whole (`TextLayout::fittingWidth`; a field's view scrolled to its caret is clipped to its box instead), `Ellipsis` is SkParagraph's (`setEllipsis`, one line), measured as the whole text all the same; several lines wrap instead. `TextEditing` is the editing model, no Div: the text (an `icu::UnicodeString`), an anchor and a caret (the selection is the sorted pair; Shift extends it), the column line moves keep, `multiline` (one line turns inserted line returns into spaces) and `readOnly` (edits refused; selecting, moving and copying kept); `insert` (the caret moves by what was inserted), `erase`, `move(direction, unit, extend)` by grapheme, word (the previous word's start, the next word's end, past whitespace, on every platform), line, line edge or all, `selectAt(index, clickCount, extend)` (caret, word, sentence, all) and `dragTo`, and `handleKey(key, mod, geometry, clipboard)`; it owns the ICU grapheme, word and sentence iterators (made on first use, pointed at the text before each) and emits nothing: every operation returns an `Edit` mask (`None`, `Caret`, `Text`) and its owner tells the world. Line and line edge moves ask a `TextGeometry` (`text/TextGeometry.hpp`: `caretRect(index)`, `indexAt(x, y)`), which `Text` implements in its own coordinates; the clipboard is a `TextEditing::Clipboard`. Its tests need no Div (`tests/text/text_editing_tests.cpp`, a fake monospaced geometry). `TextLayout` wraps SkParagraph (shaping, bidi, font fallback, wrapping, alignment) and answers the geometry: `caretRect(index)` (a zero-width rectangle a line high) and `indexAt(x, y)`; indices are UTF-16, and it keeps the text once, as the `std::u16string` its paragraph is built from. Colors aren't part of the layout: `paint(canvas, x, y, color)` paints through a `ParagraphPainter` that gives every glyph run that color, so a color transition never builds or lays out the paragraph again (SkParagraph's `updateForegroundPaint` would not: a painted line keeps its runs' paints in cached text blobs until it is laid out again; `TextLayout::paragraphsBuilt()` counts builds for tests), and `paintSelection(canvas, x, y, begin, end, background, foreground)` fills the range's rectangles (`getRectsForRange`, a line high, in visual order) and paints the text inside them again in the selection color. Every line is exactly the line height (a forced strut, half-leading). Glyphs are always positioned to the subpixel and hinted slightly, which keeps linear advances (normal hinting rounds advances to whole pixels and crowds small text). How their edges are smoothed is the inherited `fontSmoothing` style property: `FontSmoothing::None` (aliased), `Grayscale` (the default) or `Subpixel` (LCD, wrong in layers with opacity or transforms, which popups enter with). The caret is painted in `caretColor` (`color` while unset) and selected text in `selectionColor` over `selectionBackgroundColor`; all three are inherited, so a field's parts take its colors. Fonts come from `StyleManager::fontCollection()`: the loaded fonts by name (a `TypefaceFontProvider`), then the system's, which also fill in missing characters. Measuring (`maxContentWidth`, `lineCountAt`) lays the paragraph out at other widths without disturbing the layout used for painting.
- **Icons** (`psychic-ui/icons/`): vector icons as data, an `IconDefinition` (name, square grid, elements of SVG path data, each stroked or filled; `IconSet.hpp`). `IconRegistry::shared()` holds the bundled sets, then what the application `add`s (same name replaces); each icon's path data is parsed once with `SkParsePath::FromSVGString`, on first draw, and its `SkPath`s kept. An unknown name, or data that doesn't parse, draws nothing and is reported once on stderr. Two ways to draw one: the `Icon` component (`components/Icon.hpp`, a measured Div: `add<Icon>("search").size(20)`, `name("x")` changes it), and, inside skins, `paint::icon(canvas, name, rect, color, strokeWidth)` (`paint/Icon.hpp`). Both draw in `color`, the grid filling a square whose corner is snapped to a device pixel (when the canvas only scales and translates), with round caps and joins. Two inherited style properties: `iconSize` (default 14, Pivotal's medium) and `iconStrokeWidth`, in units of a 16-unit grid whatever the icon's grid (default 1.3, Pivotal's `--icon-stroke`), so every icon has the same weight at a given size. The bundled tables are generated by `tools/icons/generate.py`, never edited by hand: `PivotalIcons.cpp` from Pivotal's `packages/ui/src/icons/icons.tsx` (`generate.py pivotal <icons.tsx>`; 16-unit grid; names are its component names in kebab case without `Icon`, and `StarIcon`'s filled form is `star-filled`), then `LucideIcons.cpp`, the Lucide icons Pivotal's set lacks, under Lucide's names (`generate.py lucide`: the names listed in `tools/icons/lucide.txt`, from lucide-static 1.64.0, which the script downloads from npm at generation time, never at build time, and checks against its pinned npm integrity hash; `--package <dir>` reads an extracted one instead; it refuses a name Pivotal's set has). Lucide is ISC (some icons MIT, from Feather): the license is in the generated file's header and in full in `psychic-ui/icons/LICENSE-Lucide.txt`. To add a Lucide icon, add its name to `lucide.txt` and run the script. Normalization: each set's grid fills the icon's box (Pivotal 16 units, Lucide 24, whose glyphs cover about the same share of their grid), and strokes take one weight from `iconStrokeWidth`: Pivotal's own 1.3/16, which is within 3% of Lucide's 2/24.
- `lib/psychic-color` is the author's own color library (submodule), used for theme colors.
- `extlib/rxcpp` exists but is not wired into the root build.
